- **A stored login is a key, and it goes only to the service it belongs to.** Claude Code's `token` kind (`claude setup-token`, `CLAUDE_CODE_OAUTH_TOKEN`) is gone: Anthropic's terms forbid a developer to store a Claude.ai session token, so a subscription signs in inside the harness's own session and Sail never holds it. `sail agent login claude-code --kind token` and `PUT /v1/logins/claude-code/{name}` with `kind` `token` are refused: "Claude Code takes no login of kind 'token'; it takes api-key, glm." `api-key` is now Claude Code's default kind, so `sail agent login claude-code` stores an API key and a refusal's command names `--kind` only for another kind. The database schema is v1005: a run's `login_kind` takes `api-key` and `glm` and no longer `token`, so a box is reinstalled (`ci/fleet`'s `SCHEMA_CHANGED_IN` is 0.76.0), and a v1004 database is refused at the start naming the reinstall. With no kind of a known end, the warning of a login in its last 14 days is gone: the `ending` outcome of `agent_login_outcome` and `sail spec dispatch --json`'s `login_ending`.
- **Claude Code takes a GLM Coding Plan key.** `sail agent login claude-code --kind glm` stores one ("GLM Coding Plan key"; made at z.ai/manage-apikey/apikey-list, or a Team Plan's at z.ai/manage-apikey/coding-plan/team/my-plan); a run or session on it gets `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_BASE_URL=https://api.z.ai/api/anthropic`, and Z.AI maps Claude Code's models to its own. It is listed, used, made the default and removed like any login. A run on it records its tokens and no dollars, since Claude Code prices every run at Anthropic's rates.
- **A stored key goes to its own service against the container's environment and the harness's user and project files.** A Claude Code key's lines now set its address (`ANTHROPIC_BASE_URL`: `https://api.anthropic.com`, or Z.AI's for a GLM key), `ANTHROPIC_UNIX_SOCKET` empty (set, it carried every request to a socket the container chose) and `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST=1`, so Claude Code ignores an address, a provider or a credential that a user, project or managed settings file names; before, a container's profile export or a settings file's `env.ANTHROPIC_BASE_URL` received the person's key. They also set empty the credentials a host hands Claude Code by file descriptor, `ANTHROPIC_CUSTOM_HEADERS`, and the Mantle, Claude Platform on AWS and Claude on Google Cloud switches beside Bedrock, Vertex and Foundry's. An interactive API-key session, whose `apiKeyHelper` that flag would ignore, pins the address in its own `--settings` instead. A Codex run on a stored key now declares Sail's OpenAI provider on its command line, as an interactive session already did, so a user `config.toml`'s `openai_base_url` or `model_provider` no longer receives the key. Not closed here, and owned by the draft spec `sail-a-stored-login-never-enters-the-container`: a proxy with a CA file that the container's profile exports (`HTTPS_PROXY` with `NODE_EXTRA_CA_CERTS`, `CODEX_CA_CERTIFICATE` or `SSL_CERT_FILE`) reads the key in either harness; the interactive API-key session follows managed settings' `env` and a settings file's proxy and CA; Codex follows `/etc/codex/managed_config.toml`, `/etc/codex/requirements.toml` and a user `config.toml`'s `[model_providers.sail] model_catalog_url`; and anything running in the container can read the harness's environment.
- **A run's login outcome says only what can happen.** With the host flag no settings file's `apiKeyHelper` or key, no key `/login` kept and no signed-in subscription stands in for a stored key, so the `refused_other` and `overridden` outcomes of `agent_login_outcome` are gone, and so is a run's `login_overridden` (the column in the v1005 schema, `GET /v1/runs` and `sail agent sessions --json`, and the run's synced row).
- **`sail agent login`, `use` and `remove` refuse in JSON under `--json`.** The refusal is the API's error envelope with its code, as `sail agent login list` already did: `--kind token --json` prints an `error` with the code `invalid_request` and the message "Claude Code takes no login of kind 'token'; it takes api-key, glm.".
- **The agents route says how a subscription signs in.** `GET /v1/projects/{p}/workspaces/{w}/agents` gives each offer that starts inside (`inside` true) a `sign_in` remedy: Claude Code's "Start Claude Code here and run `/login` in it to sign in with your Claude subscription" (the command run `elsewhere`), and Codex's "Turn on device code login in your ChatGPT security settings (in a ChatGPT workspace, its admin turns it on in the workspace's permissions), then start Codex CLI here and choose Sign in with Device Code". `kinds[]` lists Claude Code's API key, then its GLM key.
