- **A workspace's sessions listing names the caller's chats beside their terminals, each with its state.** `GET /v1/projects/{p}/workspaces/{w}/sessions` now gives every row a `form`: each terminal `"terminal"`, as before, and each of the caller's own chats in that workspace `"chat"`, as `{"name", "form", "live", "state", "opener", "agent", "created_at"}`, where `name` is the id its chat routes take and `live` turns false once it ended. One list, newest first, then by name. `state` is `ended`, `needs_you` (a request the agent asked is unanswered), `working`, `error` (its last turn failed), `your_turn` (the turn ended, or was stopped or cut) or `idle` (nothing sent yet), read from the chat's log alone: listing asks no process and starts none, so a process ending while idle changes nothing a person sees. A chat is listed to its opener alone, an admin included; open chats are listed, ended ones for 10 minutes, at most 200; an older one is still read by its id. On a box with no terminal door (no `terminal-listen`) the listing is the caller's chats alone, where it was `404 terminal_not_offered`; with one, its host's refusals, an unreachable host's too, still refuse the whole answer, so no list silently leaves out live terminals.
- **The agents route says which harnesses chat, in which modes, and whether a chat may sign in inside the workspace.** Each offer gains `forms` (`["terminal", "chat"]` for Claude Code, `["terminal"]` for Codex) and, for a harness that chats, `chat` `{"modes", "mode_default", "inside"}`: the chat's modes in the words a person reads (Asks first, Edits freely, Plans first). A chat's open reads the same harness seam, so the two never disagree. One switch says whether a chat may use the sign-in a person made inside their own workspace, which Sail never holds, copies or relays; it is on for Claude Code, the owner's stated default for internal staff. Were it off, `chat.inside` would say false and an `inside` open, or the next start of a chat opened inside, would be refused (`422`, "Claude Code's chat takes your stored API key here, not the sign-in made in the workspace."); a stored API key is always offered.
- **A person says whether they start in Chat, Terminal or both.** `GET /v1/me/preferences` answers `{"session_form"}`, `chat` for anyone who never set it; `PUT /v1/me/preferences {"session_form": "chat" | "terminal" | "both"}` sets it and answers it. Any other value (`422`, "session_form is chat, terminal or both.") or field (`422`, "A preference names only session_form.") is refused, and nothing else under `/v1/me/` is served. Each person reads and sets only their own, a viewer too, through a new Access action, Keep preferences (viewer, member and admin yes; work agent, room agent and the in-container credential no), which writes no synced row; a token that acts for no person holds none (`403`). The preference is kept on the box the app talks to, never synced, and goes with its person.
- **The database schema is v1008.** The box-local `preferences` table is new; a v1007 database is refused at the start naming the reinstall, so a box on a release is reinstalled once for this release's chats (`ci/fleet`'s `SCHEMA_CHANGED_IN` is 0.79.0).
