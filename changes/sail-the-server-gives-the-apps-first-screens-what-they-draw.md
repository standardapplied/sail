- **A person lists and removes their own passkeys over HTTP.** `GET /v1/passkeys` answers `{"passkeys": [...], "total": n}`, oldest first, each `{"id", "label", "created_at", "last_used_at"?, "current"}`: the credential id as base64url, `last_used_at` absent until first used, `current` true for the passkey the calling session was signed in with. `DELETE /v1/passkeys/{id}` removes one and ends every session it signed in, answering `204`. Only a session signed in with one of the person's passkeys that still exists removes one: a person's token, at any role, a session that names no passkey, and one whose passkey an admin removed with `sail fde passkey rm` are `403 forbidden` ("Passkeys are removed only from a session signed in with a passkey."), the same for every id; an agent asking is told only its person may. Another person's id is `404 not_found` ("No passkey of yours has that id."), as an id that names none is; the last passkey ("This is your only passkey, so removing it would leave you no way to sign in.") and the one the caller signed in with ("You are signed in with this passkey.") are `409 conflict`, the last said first. The decision and the removal are one write transaction, so two removals at once never leave a person without a passkey, and a sign-in whose passkey is removed while it finishes mints no session. Both routes are a new Access action, Keep passkeys (viewer, member and admin yes; work agent, room agent and the in-container credential no), which writes no synced row, so a viewer stays read-only. An admin still removes another person's with `sail fde passkey rm`. A session records the passkey it was signed in with (`sessions.credential_id`; none for the SSH gateway's sessions or a token), so the database schema is v1006: a box is reinstalled (`ci/fleet`'s `SCHEMA_CHANGED_IN` is 0.77.0), and a v1005 database is refused at the start naming the reinstall.
- **The app's first screens get the words they draw from the server.** `GET /v1/projects/{p}/template` sends `step_names`, as long as `steps`: the `ProjectPhase`s lower-cased in order (`container_launched` … `complete`), then `template_finished`, so step n of `build.step` is `step_names[n-1]`. Each mode a workspace offers says `risky`, true only for Claude Code's `bypassPermissions` and Codex's `full-access`, which skip the harness's own permission checks. An offer with a `refusal` carries `unavailable`, the few words a list row says ("Not installed in harbor"), declared with the refusal it shortens. `GET /v1/agents` gives each harness its `sign_in` (`name`, `how`) and `kinds`, from the mapping the workspace route uses. `POST /v1/projects` refused for a name taken ("A project named harbor already exists.", "Choose another name, or open harbor.") or held by an instance names `name` in `field_errors`; `sail project create` and `sail project rename` say the same sentence, without quotes around the name. The client goldens record `health`, `agents`, the passkey routes and their refusals, a project created, its name taken and a control plane with no project.
