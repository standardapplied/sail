- **A change's entry is a file of its own, and the release folds them in.** Every pull request added its entry at the top of `CHANGELOG.md`, so each merge conflicted with every other open pull request, which then needed main merged and a full CI run again. A pull request now adds one file, `changes/<short-slug>.md`, holding its bullets as they would read under the version heading (`changes/README.md`), and never edits `CHANGELOG.md`: `ci/check changelog` (`ci/changelog check`), run by bare `ci/check` and by CI's first job on every pull request, refuses one that adds, removes or rewords a line of it, naming the file to add instead, and refuses an entry the release could not fold (no bullet first, Windows line ends, anything but a `*.md` file directly in `changes/`), so a malformed entry fails its own pull request. The release runs `ci/changelog X.Y.Z` in the version bump's commit, on a full clone: it puts every file's bullets under a new `## X.Y.Z` at the top of `CHANGELOG.md`, oldest file first by the commit that added it, and removes the files, refusing a version already there, an empty `changes/` and a malformed entry before writing anything. `release.yml` refuses a tag whose commit did not fold (`ci/changelog released X.Y.Z`: no entry left, `CHANGELOG.md` starting at the tag's version), before anything ships. The unreleased 0.75.0 entries moved to `changes/`, one file per change; a fragment, like the changelog, starts no CI lane.
