- **The server says who may build a template.** `GET /v1/whoami`'s `capabilities` gains `build`, after `read`, `write` and `admin`, when the caller's role and lane may build a project's template: the decision `POST /v1/projects/{p}/template:build` takes (an admin on the API, the CLI or sync; never the in-container credential or an agent), so a client offers a build, or a create that ends in one, by `build` instead of inferring it from `admin`. Who may build is unchanged.
- **A definition that clones two repositories to one path is refused.** `POST /v1/projects` and `PUT /v1/projects/{p}/definition/repos` answer 422 `invalid_request` ("More than one repository is cloned to app: give each its own path.") with a `field_errors` entry for each such row, `{"field": "repos[0].path", "message": …}`, where the build used to stop at its clone step; `app` and `app/` are one path, and a repository inside another's (`app/web` and `app`, in either order) is refused the same way ("app/web is inside app, another repository's path: clone each outside the other."). The rule is held where a definition is written, so one stored or synced before it is still read, repaired, deleted and synced. `sail project repo add` says the same sentence for a path the project holds, instead of "Repo with path 'app' already exists.", and a `--json` refusal of the CLI carries the `field_errors` the API would. A section's write is decided before its value is checked.
- **An invalid project name names its field.** `POST /v1/projects` refused for a name the project-name rule refuses, or one ending `--tmpl`, carries `field_errors` `[{"field": "name", "message": …}]`, its message the refusal's own, as a taken name does. The client goldens record whoami's `build`, the invalid name and both repository refusals.
