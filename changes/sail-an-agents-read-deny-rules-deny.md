- **A Claude Code agent's read-deny rules now refuse what they name, in every lane.** Sail writes `permissions.deny` rules into both settings files a Claude Code agent runs under, `~/.sail/claude-settings.json` (every spec run: build, review, fix) and `~/.sail/claude-live.json` (a room's live member), to keep it from reading the workspace user's `~/.ssh`, `~/.git-credentials`, `~/.config/gh`, a run's `launch.env` and the box credential. Before this release, every one of them but the box credential's did not bind: they were written with one leading slash (`Read(/home/dev/.ssh/**)`), which Claude Code reads from the settings file's own folder, so they matched nothing. That was so since each was added: `~/.ssh` and `~/.git-credentials` in 0.24.0, `~/.config/gh` in 0.47.0, `launch.env` in 0.69.0. On 0.77.0 (recorded on Claude Code 2.1.332), an agent in the full lane (`--dangerously-skip-permissions`, which every spec run and a full room member use) read all four with its Read tool and with `cat`, never asked: the dev user's SSH key, the git and `gh` forge tokens, and, while a run's `launch.env` was there, that run's credential and its person's login. A read-only room member was kept from them only because they lie outside its workspace and nobody can answer its prompt, never by the rule. Each rule is now written `Read(//…)`, from the root, and so is the new one for the login file a workspace's agent session is handed under `~/.sail/sessions`, and the same recordings show each one refusing Read and `cat` of every path it names in both lanes: a deny rule binds under `--dangerously-skip-permissions` too. One place builds the list (`ClaudeCode.readDenyRules`); the files change on the next `sail project apply` or dispatch, as every Sail-owned file in a container does. Codex is given no such rule: the one it has, a permission profile's `deny`, is enforced by its sandbox, which cannot start in a workspace, and Sail runs Codex without it.
- **`ci/fleet`'s loop proves the `~/.ssh` rule on a real run.** In the `rebuilt` group, a third spec on eng asks its full-permission build which file to read. The row writes a random canary to a file under `~/.ssh` in that spec's workspace with `sail project exec`, which runs a command in the instance it names, the spec's workspace among them, and reads it back just before it answers with the path. It passes only when the file still holds the canary at the end, no run's log, comment of the spec, file of the workspace outside `~/.ssh` or commit there holds it, and a run's log holds Claude Code's refusal by the rule; a file never written fails it. The spec and its workspace are deleted after, whatever happened.
