- **A Claude Code agent's read-deny rules now stop its ordinary reads of the files they name, in every lane; they are not a boundary.** Sail writes `permissions.deny` rules into both settings files a Claude Code agent runs under, `~/.sail/claude-settings.json` (every spec run: build, review, fix) and `~/.sail/claude-live.json` (a room's live member), naming the workspace user's `~/.ssh`, `~/.git-credentials`, `~/.config/gh`, a run's `launch.env` and the box credential. Before this release, every one of them but the box credential's did not bind at all: they were written with one leading slash (`Read(/home/dev/.ssh/**)`), which Claude Code reads from the settings file's own folder, so they matched nothing. That was so since each was added: `~/.ssh` and `~/.git-credentials` in 0.24.0, `~/.config/gh` in 0.47.0, `launch.env` in 0.69.0. On 0.77.0 (recorded on Claude Code 2.1.332), an agent in the full lane (`--dangerously-skip-permissions`, which every spec run and a full room member use) read all four with its Read tool and with `cat`, never asked: the person's forge (GitHub) token, which git reads from `~/.git-credentials` and `gh` keeps in its login, and, while a run's `launch.env` was there, that run's credential and the person's harness login it carried. A workspace's `~/.ssh` holds no private key, only the owner's public keys in `authorized_keys`; its rule stays because it costs nothing. A read-only room member was kept from them only because they lie outside its workspace and nobody can answer its prompt, never by the rule. If an untrusted prompt (a spec, a room message, a file in a repository) could have reached a full-lane agent on your boxes before this release, consider revoking that person's forge token at the forge, then giving Sail a new one with `sail git login <host>`, and revoking their harness login or API key at its provider (what a run's `launch.env` carried, and any sign-in kept in the workspace), then signing in again or storing a new key: a token an agent read stays valid until it is revoked. A run's credential ends with its run. Nothing about file ownership protects these: the agent's user has passwordless `sudo` in its workspace. Each rule is now written `Read(//…)`, from the root, and so is the new one for the login file a workspace's agent session is handed under `~/.sail/sessions`. Two files Sail itself writes are added, as exact paths in the same form: `~/.git-credentials.sail-new`, the store written whole before it is moved in, and `~/.sail/gh-token`, the file `gh` is handed its token in; a give or login cut short leaves either behind. The harness's own stored login (Claude Code's `~/.claude/.credentials.json`, `~/.claude.json` and `~/.claude/backups`, Codex's `~/.codex/auth.json`) is not in the list, and an agent can read it. Recorded for `~/.ssh` in both lanes, under `--dangerously-skip-permissions` too, a rule now refuses the Read tool (directly, through a symlink and in a subagent) and the Bash reads Claude Code checks against it: `cat`, `head`, `tail`, `cp`, `base64`, `od`, `grep -r`, `find -exec cat`, `awk`, `sed` and `git diff --no-index`, whether the path is spelled with `$HOME`, `..` or after `cd`. It does not stop `less` or `more` piped on, `python3 -c` with `open()`, `tar`, `dd`, `xxd`, `sh -c` or `bash -lc` around a `cat`, `git hash-object` then `git cat-file`, a hard link into the workspace then Read, or a command that only uses the file (`ssh-keygen -y -f`): a full-lane agent runs those unasked, so one that sets out to read these files still can. In the asking lane a person sees each such command before it runs, except the Read of a hard link. Keeping what a workspace holds in trust from an agent that tries, the harness's own stored login among it, is the boundary spec `sail-an-agent-cannot-read-what-its-workspace-holds-in-trust`. One place builds the list (`ClaudeCode.readDenyRules`); the files change on the next `sail project apply` or dispatch, as every Sail-owned file in a container does. Codex is given no such rule: the one it has, a permission profile's `deny`, is enforced by its sandbox, which cannot start in a workspace, and Sail runs Codex without it.
- **`ci/fleet`'s loop proves that a full-permission agent's Read of a file under `~/.ssh` is refused, and that the file's content is in no log, comment, other file or commit.** In the `rebuilt` group, a third spec on eng asks its full-permission build which file to read. The row writes a random canary to a file under `~/.ssh` in that spec's workspace through the workspace's shell (`sail project workspace shell`, fed the command with no terminal), Sail's one way to run a command in a workspace, and reads it back just before it answers with the path; the agent is asked to read it with its Read tool and with `cat`. The row passes only when the file still holds the canary at the end, a run's log holds Claude Code's refusal by the rule, and no run's log, comment of the spec, file of the workspace outside `~/.ssh` or commit there holds the canary; a file never written fails it. It proves the ordinary read is refused, not that the content cannot be obtained another way. The spec and its workspace are deleted after, whatever happened.
