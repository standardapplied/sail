- **A read of a workspace's file is proved by its content.** The read hashes (SHA-256) the bytes it sends, hashes the same range of the file again after them and stats it again, and ends with its bytes only when both digests and both versions agree; its last `FilesData` frame carries that digest (`digest`, the content version of what was read, blank on the frames before), else the read is refused `changed` and the client reads again. Stats alone let a read spliced across an in-place write through whenever both stats fell inside one write's tick of a coarse clock: measured with a tight in-place writer, 271 to 807 of 2,000 reads on this devbox's ext4 and 33 to 51 on a GCP runner's, none on ZFS; the second digest caught all but 6 of them, each a file left half-written through both passes, which is what it then held. A save's base is a whole read's digest. A 20 MiB read hashed twice is measured in `WorkspaceFilesIT` and on the fleet's storage row. A digest is a SHA-256 in lowercase hex or the read fails: the script checks its two and the host the one it answers, a workspace with no `sha256sum` is said so ("dock has no sha256sum, so Sail cannot prove what it reads of …; nothing was changed."), and a failing `dd` fails the read rather than reading as `changed`. The last frame says whether the read was whole (`whole`: from 0 to the file's end), the only digest a save takes as its base, so a file over 20 MiB, never read whole, is never saved. Within the same unreleased `SAILPTY7`: `FilesData` gains `whole` and `digest`.
