- **The app's drive keeps to its own account and its own folder, and puts back what it shares.** `ci/drive` ended every process on the Mac whose command line held `_pty-host --local`, so on a Mac shared with a person it reached for their terminal host. It now looks only at this account's processes (`pgrep -U`) and ends only what its own runs started, by their pids: the drives writing into its output folder, the terminal hosts Sail apps start from Application Support (before the runs that need none, and when it ends), and the feeder of the third run's attach client. It does not run while this account already has such a host, since that host's terminals would end with it. The drive build keeps Sail's own identifier, which its signed runs need (the App ID, the Keychain access group, passkeys), so it shares Sail's settings: `ci/drive` saves this account's settings before the runs and puts them back exactly when it ends, and does not run when they cannot be saved. `ci/test-suites` and the drive's `kill` step look only at this account's processes, and the third run's step ends only its own client. The drive's flood files, colour asker and flood pacer, made at fixed paths in `/tmp`, are made in the run's private folder, which `ci/drive` hands over as `SAIL_DRIVE_PRIVATE` (the drive refuses to start without it, and scripts name it as `{private}`) and removes when it ends, so two runs on one Mac never share a file. `ci/drive-check`, run by `ci/test-suites`, proves on stand-ins that another account's host lets the drive go on and this account's own host, or settings it cannot save, stop it before anything starts; the app lane proves after the drive that the settings are as they were, no feeder is left and a second `ci/drive` on the same account starts.
