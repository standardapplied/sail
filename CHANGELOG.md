# Changelog

## 0.69.0

- **Reinstall every box to take this release: its database schema changed (v1004) and no database before it is converted.** A box on 0.68.0 refuses to start on 0.69.0 with "Database schema v1003 was made by an earlier Sail release; this release opens only v1004 and converts none: the box is reinstalled." and the remedy to move the database aside and run `sail init`. The sync wire is protocol 9: a 0.69.0 main refuses a 0.68.0 node at the hello and tells it to reinstall, so no run crosses through a box that drops the login it started with. After reinstalling, each person stores their harness login again (below), or their spec runs are refused.
- **A run of a spec starts its harness with a login its person stored, and no secret of a run is ever on a command line.** `sail agent login <harness>` reads an API key or a long-lived token from stdin (a terminal echoes nothing) and stores it as `default`, or under `--name`, in root-only files on the runner (`/var/lib/sail/logins/<fde-id>/<harness>/<name>`, `0700` directories, `0600` files, written whole and renamed), outside the database and never synced; it prints the name, kind, whether it is the default and the first eight hex digits of the value's SHA-256, never the value. Claude Code takes a `token` from `claude setup-token` (`CLAUDE_CODE_OAUTH_TOKEN`) or an `api-key` (`ANTHROPIC_API_KEY`); Codex an `api-key` (`CODEX_API_KEY`, which every `codex exec` reads first) or a `token` (`CODEX_ACCESS_TOKEN`). A value is one line of printable ASCII with no space, quote, backslash, `$` or backtick, at most 16 KiB; a refusal names the rule, never the value. `sail agent login list [--fde <handle>] [--json]`, `sail agent login use <harness> <name>` and `sail agent login remove <harness> <name> [--fde <handle>]` list, switch and remove; a switch applies to launches after it, and removing a login live runs started with says they finish on it. On the host they are root's and act as the box's person; anyone else reaches the same doors (`GET /v1/logins`, `PUT /v1/logins/{harness}/{name}`, `POST /v1/logins/{harness}/{name}:use`, `DELETE /v1/logins/{harness}/{name}`) through the gateway lane or Mast. A new Access action, **Keep logins**, is yes for every person, a viewer included, and no for agents and the credential in a project container; another person's logins are listed or removed only by an admin (Manage people). Each change is announced (`login_stored`, `login_default`, `login_removed`) with its person, harness, name, kind and fingerprint.
- **Runs of spec work no longer use a login made by hand in the project's container.** A build, review, fix and every lane of a spec's room starts with the stored default login of the person it acts for (an admin's dispatch of another person's spec spends that person's login), and is refused before anything is reserved when there is none: "No Claude Code login stored for uday, so a run of a spec cannot start: a login made by hand in the project's container is not used by runs.", naming how to make each kind and the command that stores it, with its own error code, `login_not_stored` (409; SailKit's `ErrorCode.loginNotStored`). A dry-run dispatch is refused the same way. When a room wake, a resumed build, a review, a fix or a dispatch is refused so, the spec's room is told once, naming the person, the harness and the commands that fix it, and not again for the same cause until a run of the spec starts. An ad-hoc run and a member of a room with no spec still use the container's own login. The run records `login` (the name, or `container`), `login_kind` and `dispatched_by` (the person whose request launched it; none for the loop, a room wake or a resumed build), synced with the run.
- **The run credential and the login reach a run only in its `launch.env`.** Each launch pushes `/home/dev/.sail/runs/<run>/launch.env` (`0600`, the dev user's) through the one push helper (`ContainerFilePush.pushAsDev`, which `project apply` and the `gh` login use too), and every launch shape's wrapper starts with the same fixed text, which turns tracing off, exports each line as it is and removes the file before the harness starts, or ends the launch when there is no file. The file sets every other credential variable the harness reads empty, so a key the container's profile exports cannot outrank the stored login. `systemd-run --setenv SAIL_RUN_CREDENTIAL`, the foreground wrapper's assignment and the live member's `incus exec --env SAIL_RUN_CREDENTIAL` are gone, and with them the redaction of launch commands shown to listeners. The room lane's read-deny rules gain `launch.env`. On the host every pushed file is staged in the account's own `0700` staging directory (`/tmp/sail-staging-<user>`), never anywhere readable by others, and a launch released before its agent started removes its `launch.env` at once. The missed-stop reconciler's 60-second pass removes the `launch.env` of every run of the box that is not live (asking only containers a run started or finished in since its last pass), what a killed push left in the staging directory, and the logins of every person the roster no longer holds (asking the roster just before each delete, so a person added meanwhile keeps theirs); removing a person deletes their logins once the removal commits.
- **No hook puts a credential on a command line.** The event helper, the session report, the room relay, the stop gate and the spec, skill and portal helpers sent `Authorization: Bearer <credential>` as a `curl -H` argument, so every hook call showed the run credential in the host's and the container's process lists. Each now sends it through one shell function, `sail_curl`, which hands curl the header as a config on a file descriptor fed by the shell's built-in `printf`: in no argv, no environment of a process it starts and no file.
- **A login's directories are the runner account's alone, `0700`, whatever the parent gives.** Each directory under `/var/lib/sail/logins` is set to this account's user and group and mode exactly `0700` when it is made and whenever it is found otherwise, so a setgid data directory no longer leaves one `2700` with the parent's group.
- **The Claude Code token's remedy no longer says `sudo claude setup-token`.** It says to run `claude setup-token` on a machine where Claude Code is signed in, then store the token with `sail agent login claude-code`.
- **`sail agent login --dry-run` says what it would store** (harness, name, kind, the default or not) and reads and stores nothing; `remove` of a login not stored says there was nothing to remove and succeeds. A thin client runs every storing `sail agent login` over a terminal, so a typed value is never echoed, and piped input is said to be read from stdin.
- **The fleet's loop stores each agent's key with `sail agent login <harness> --kind api-key`** and writes no key into the container; it checks that the build's run says `login=default`, `login_kind=api-key`, and that no key is in any process's command line while it builds.

## 0.68.0

- **Reinstall every box to take this release: its database schema changed (v1003) and no v1 database before it is converted.** A box on 0.59.0 to 0.67.0 refuses to start on 0.68.0 with "Database schema v1002 was made by an earlier Sail release; this release opens only v1003 and converts none: the box is reinstalled." and the remedy to move the database aside and run `sail init`. Nothing is half-upgraded: the refused database is left exactly as it was. The sync wire is protocol 8: a 0.68.0 main refuses a 0.67.0 node at the hello and tells it to reinstall (a 0.58 node, whose database `sail upgrade` still converts in place, is told to upgrade as before; a node on any other older release, 0.57 included, to reinstall), so a staggered reinstall never syncs runs or specs through a box that drops their cost and times. Export any measures you want to keep (`sudo sail spec list --all-projects --status done --measures --json`) before reinstalling.
- **A shipped change records what it cost where it happened: tokens and dollars per run, when it became ready and done, and the minutes people gave it.** Each harness reads its own report of a run (`Harness.usage`): Claude Code the last `result` line of the run's stream-json log (tokens summed over `modelUsage`, so subagents count, dollars from `total_cost_usd`, the model that cost most), Codex its rollout transcript's last `token_count` and model (no dollars). The finish writes it, with the model reported and the effort passed, in the update that makes the run's row terminal; a report that says nothing, or a report file that is not there, is `usage_source: none` with null counts, never zeros. A harness session's report is its running total, so a run records its share: the report less what the session's other runs were given, kept per session on the box (`session_usage`) where retention never reaches, and a resumed run's session is stamped at launch. A report below what its session already reported (an earlier run finishing late, a harness that started counting over) tells no share: it is `usage_source: unattributable`, adds nothing, and its spec's tokens and dollars are served as a lower bound. A live member sets each turn's share and keeps the last as it finishes. Runs carry `model`, `effort`, `tokens_in`, `tokens_out`, `tokens_cache_read`, `tokens_cache_write`, `cost_usd` and `usage_source`, synced with the run as its executing box's fact. The report is read in one command bounded at 10 s: for each of the harness's markers, the last lines of the file holding it (`tac | grep -m 16 -a -F` per marker, so a Codex turn's many counts never hide its model), so a long log with no result line is `none` at once. A last report line that does not parse is `none`, said once on stderr; a raw C1 control, U+FFFE or U+FFFF in it, which JSON allows, parses. Only a report whose container did not answer (stopped, missing or silent past 10 s) is left unread, never taken for none: retention keeps the run's directory, and each reconciler sweep reads it again until it is answered. An operator's stop no longer waits on reading it.
- **A spec's ready, awaiting-merge and done times are its moves' own, the same on every box.** `ready_at` is its first move into `pending`, written once; `awaiting_merge_at` its latest move into `awaiting_merge`; `done_at` its latest move into `done`, cleared when it is reopened and kept when it is archived. Each is stamped from the moving revision and carried in the snapshot like `archived_at`, so main and every node hold the author's times. Measures read them, and `collapsed_by_sync` and `history_incomplete` are gone.
- **A spec's runs are counted where retention cannot erase them from under it.** Each box keeps, on the spec, the runs, builds, fixes, runs without usage or dollars, tokens and dollars of every finished run it holds, folded as the run finishes; erasing a run lowers nothing. Build and fix runs still running are counted as rework under way. A box that may lack a run serves its run figures as a lower bound (`at_least`): one that first held a spec after main erased a run of its project made after the spec, and one that adopted main's erasure of a run it never saw finish. Tokens and dollars are exact only when every run counted reported them: a lower bound when some did not, and unknown (`runs_not_reported`) when none did. Two boxes never serve two different exact numbers for one spec.
- **The minutes people give a change are recorded on the box that saw them.** A box-local `attention(person, conversation, minute, channel)` table, never synced, holds one row per minute: a person's accepted input in a room-bound terminal (`terminal_input`, told by the terminal host once a minute per connection), a post (`post`), a review decision or a status move (`review_act`), and `POST /v1/attention {"conversation": ...}` from a client whose view is focused with recent input (`focus`). Only a person on a person's own lane counts, never the credential in a container or a run's principal; the server stamps the person and the minute, and a conversation the caller may not read answers as a missing one. Nothing else about a person is stored.
- **Measures show cost, budget and human minutes.** `sail spec show`, `sail spec list --status done --measures` and their routes now serve the runs' tokens and dollars with the runs behind each, the project's `agent.budget: {tokens, usd}` (both optional, a bad value refused naming the key) and `over_budget` (display only), human minutes as distinct (person, minute) pairs in the spec's own conversation by channel, with the count of people and the box named, always a lower bound, and "no recorded human code act" also requires no `terminal_input` minute in the spec's own conversation. The listing summarizes tokens and dollars over the values known exactly, counting the lower bounds and unknowns it leaves out, and human minutes as this box counted them.
- **A reasoning effort is passed or refused, never dropped.** Claude Code is launched with `--effort <level>` (it takes `low`, `medium`, `high` and `xhigh`); Codex keeps `model_reasoning_effort`. An effort the spec's harness does not take is refused naming the harness, as `invalid_request`, before any run is reserved: at the spec door when the agent or effort changes (a spec already holding one still moves and is retitled), the dispatch door, a room wake and the launch; the old "dropping reasoning_effort" warning is gone.
- **SailKit sends the focus heartbeat.** `Endpoint.attention(conversation:)` posts it, and `FocusHeartbeat` says when one is due: at most once a minute, only while the view is focused and the person gave input in the last minute.
- **A box with two disks gets a ZFS pool mirrored across them, so losing one disk loses no workspace.** `sudo sail host init --storage zfs --disk <a> --disk <b>` makes one pool that is a ZFS mirror of the two: Incus is handed both in its own mirror source (`incus storage create <pool> zfs source=mirror=<a>,<b>`, by their `/dev/disk/by-id` paths where the disks have a hardware identity), and runs one `zpool create -m none -O compression=on <pool> mirror <a> <b>`, never `-f`: every refusal, Sail's or zpool's checks of both devices, leaves both untouched, and a failure while zpool labels them can leave the first with its start zeroed or a new empty table and no pool (both were blank, so nothing is lost; a re-run says what it finds). A zpool already imported under the pool's name is refused before Incus is asked, for one device and a mirror, since zpool labels the devices before it finds the name taken. Each device is cleared by the one decision a single device is (`PoolDevices.cleared`): lsblk and the `/proc` walk are read once for both, every slow read of both comes before either device's probes, and at the re-check before the create the probes of both are the last commands; a refusal names which device and why, and nothing is made unless both pass. Two partitions of one disk, two paths to one disk (one WWN or serial) and two namespaces of one NVMe controller are refused: a mirror on one disk dies with it, and every NVMe persistent disk of a GCP VM is such a namespace, so those cannot be mirrored. Devices whose sizes differ by more than the 16 MiB `zpool create` mirrors without force are refused before anything is installed, naming the difference and both sizes (in bytes when they round alike); within that the output says how much of the larger goes unused. An Incus without the `storage_zfs_vdev` API extension (Ubuntu's 6.0.0) is refused before the devices are cleared again, and a dry run says so rather than what it would create; the refusal names what moves it, Zabbly's apt source and then `sudo sail host incus upgrade`, since apt itself will not replace the packages Sail holds; that command runs on a box whose first `host init` has not finished, which has no database and no session host's socket, so no agent run or terminal session for the restart to end, and it warns of none. `host init` and `host status` say `a mirror of <a> and <b>` in place of "one device: no redundancy". Re-running the command that made a mirror, in either order of its two `--disk` flags, is a no-op; one of the two, or another pair, is refused by name. What a pool is on is what ZFS lists for its zpool now, each whole-disk device as its disk, not the names Incus recorded at creation (kernel names that can move across a reboot or outlive a `zpool replace`): the re-run compares with those, and `host init` and `host status` say them; a zpool that is not imported, or does not answer, is said as Incus recorded it, saying so. A log, cache, spare, special or dedup device added with `zpool add` is no member of the mirror: the two-disk re-run still keeps the pool, and `host status` names it on a row of its own (`plus a log device /dev/sde`; `auxiliary_devices` in `--json`), while it stays a device in use. With two `--disk`, one refusal names what is wrong with each device, every command for both in the order to run them; a whole disk that holds only what a destroyed zpool left on it (zpool's table, its data partition and the 8 MiB reserved partition) is refused naming `sudo zpool labelclear <data partition>`, then `sudo wipefs --all <disk>`, which return it to blank; and the labels of a pool that can still be imported name `zpool labelclear -f`, since labelclear refuses an exported pool's device without it, for one `--disk` too. One `--disk` runs the same commands and says the same as before.
- **`host status` shows a ZFS pool's health as ZFS says it now.** Under each zfs pool's row it gives the state `zpool status -P` gives (ONLINE, DEGRADED, FAULTED, SUSPENDED, or not imported), each device that is not online on a row of its own, and on a DEGRADED pool what mends each device: `sudo zpool online <pool> <device>` for one the operator took offline, `sudo zpool replace <pool> <device> <new device>` for one gone or failed; `--json` carries it as `health` and `unhealthy`. Every read of zpool (`status`, `list`, the `import` listing) is given 10 s, and a pool whose zpool has not answered is asked nothing more in that command, so a hung pool costs 10 s and two cost 20 s: `host status` says it did not answer, shows the pool as Incus recorded it and goes on; `host init` refuses, changing nothing, as it does when the read that decides whether a device is free does not answer. Workspace and template verbs that change something go on on a DEGRADED mirror, saying once that it is, and are refused on a mirror in any other state, or whose health zpool does not tell, naming it and `sudo zpool status <pool>`; a pool of one device or a file is left to Incus there as before. Sail replaces and resilvers nothing.
- **A pool Incus did not finish making, or cannot start, is never taken for one that exists.** When incusd stops between its `zpool create` and marking the pool created, Incus 7.6 shows the pool `Pending` while it runs and `Unavailable` once it is back; a re-run of `host init` said "already exists", put the base profile on it and said "Server ready" on a box where nothing could launch. A pool Incus reports `Pending`, `Errored` or `Unavailable` is now refused, for one device, a mirror and a dir pool alike, at the flags and again before the pool step, before any profile and with no "ready", naming the status and the remedy. An `Unavailable` zfs pool whose record names no zpool is that half-made pool: `sudo incus storage delete <pool>` removes the record and leaves the zpool, then `sudo zfs list -r <pool>` and, if it lists only the pool itself, `sudo zpool destroy <pool>`, and the next run names what the zpool left on the disks. Any other `Unavailable` pool was made, and the refusal points at `sudo incus storage show <pool>` and `sudo zpool status <zpool>` to mend it. `Pending` and `Errored` name `sudo incus storage delete <pool>`, which for `Pending` leaves the zpool to destroy and for `Errored` destroys the one its record names when it holds only Incus's own datasets. `Unknown` and every other status are kept as before.
- **A template that needs a token names the sudo that keeps only that token.** Its refusal said to keep `GITHUB_TOKEN` through `sudo -E`, which keeps the whole environment, the operator's HOME and XDG directories among it, so root's incus calls left root-owned `~/.config/incus` and `~/.cache/incus` in the operator's home; it now names `sudo --preserve-env=GITHUB_TOKEN`, which keeps that variable and gives root its own home.
- **The incus CI shards run the Incus `host init` installs.** They took Ubuntu's incus 6.0.0, which cannot make a mirror; they now install Zabbly's stable repository, as every box does, unpinned: CI tests Zabbly's current stable release, and Ubuntu's 6.0.0 is covered only by the unit tests of Sail's refusal of it. Root's `incus admin init` there runs with root's own home and no XDG directories, as a box's sudo runs it, so it leaves nothing in the runner's home.

## 0.67.0

- **A project can run several workspaces on one box, each a clone of its template, made in about three seconds.** On a box with a ZFS pool, `sudo sail project workspace create <project> <name>` makes a workspace: its own container `<project>-<name>`, with its own tree, services and ports, cloned (`incus copy <project>--tmpl/v<n> <project>-<name>`, a ZFS clone whose `origin` is the snapshot) from the project's template and started, then made its own in one `incus exec`: a new machine-id, the project's name as its hostname so the in-container `spec`, event and portal helpers work unchanged, new SSH host keys made under it (a clone has the template's), every repo fetched (asked again until 10 s have passed while its host does not resolve, as a fresh clone's resolver lags its address, git in the C locale, the retries counted in `ready_steps.fetch_retries`) and switched to a branch named after the workspace (the remote's when it has one, else a new one from the repo's branch or the remote's default), sshd restarted onto the new keys, the dev user's bus waited for, the shared files pushed, sail's machinery reconciled, and last a ready mark, written with the template's own keys cleared from the clone. On a 4-vCPU cloud VM the clone takes about half a second and the whole create about three (`Created fix-login from v1 in 3.2 s (clone 0.5 s, start 0.4 s, ready 2.3 s)`), each phase measured on `System.nanoTime`; `--json` carries them as `timings` in milliseconds, the readiness step by step as `ready_steps`. A create that fails after the copy deletes the instance; one interrupted harder leaves a workspace without its ready mark, which is listed as `incomplete`, never started or entered, and replaced by the next create of its name; one whose mark was taken off by hand is refused by `create`, `start` and `shell` alike, naming `workspace delete`. Two creates of one name make one workspace and refuse the other; two of different names build a missing or stale template once and both clone it. The template is the stopped instance `<project>--tmpl`, which `sudo sail project template build <project>` (or a create that finds none or a stale one) provisions with the project's own provisioner on the box's ZFS pool (the base profile's when it is ZFS, else the one beside it; several beside a pool that is not ZFS are refused naming them; an existing template stays where it is), born with `user.sail.template.of`, recorded with `user.sail.template.current`, `user.sail.template.inputs` (the digest of the definition and the workstation key that apply records) and the highest version it was ever given, then snapshotted as `v<n>`; it does nothing when the current version was built from the definition as it is, a stale one is converged on its disk as apply converges a container, and a failed build leaves the previous version current, makes no snapshot and stops a template it started. A build whose https repos ask for credentials no token was given for is refused before it starts, naming `--git-token`, asked of every repo at once within a few seconds, following no redirect, and outside the box's pairing lock; only a `401`, or a `403` carrying an authentication challenge, counts as asking for one. `sail project workspace list <project>` lists `main`, the project's own container, then every workspace, with its state (`frozen` for a paused one, `incomplete` for an unfinished one), template version, created time and IPv4; `shell`, `stop`, `start` (which says what its resume took) and `delete` act on the one instance named `<project>-<name>` that carries that workspace's keys, and refuse, naming them, any other instance carrying them, such as a hand copy. `delete` asks once it finds the workspace, naming it and that its uncommitted work is lost (`--yes`), and refuses a missing one or `main` without asking; `create`, `delete` and `template build` are root's, as `apply` and `destroy` are. `main` is never written to, copied, snapshotted or restarted: every verb but `list` refuses it naming the project verb (`delete main` names `project destroy`). A name is the project-name rule, not `main`, not ending in `-`, at most 63 characters as an instance and no instance, project or template name already taken, each refused naming the conflict. A box with no ZFS pool refuses every verb that makes or changes a workspace before anything changes, naming `sudo sail host init --storage zfs`, and lists its default workspace alone. Every verb reads the project from the catalog as the box's person, as `project apply` does; `GET /v1/projects/{p}/workspaces` serves the same rows, read in scope (`404` for a project outside it), and `SailKit`'s goldens record its answer. The instance is the record: no row and no schema change.
- **A workspace or a template is never taken for a project.** Every command that walks the box's instances now asks one place what each is (`BoxInstances`): a project's own container, a workspace, a template, or not Sail's. A scoped box's sync round no longer deletes the workspaces and template of a project in scope (it deleted every one within a minute), and when a project leaves the box's scope it takes its workspaces and template with it, saying so for each. `project apply --all` no longer starts them or rewrites a workspace's hostname; `project list`, `GET /v1/projects` and `agent status` no longer show them as projects; `sail snaps prune` across all projects no longer deletes template versions; the boot sweep reconciles only whole workspaces; a new pairing's key reaches a project's whole workspaces. `sudo sail project destroy <project>` removes the project's template and workspaces with its container, naming each in its prompt. No new project may take a name ending `--tmpl`, and every command that addresses a container by a project's name (`project create`, `apply`, `destroy`, `start`, `stop`, `switch`, `shell`, `exec`, `logs`, `connect`, `rename`, the snapshot, resources, config, repo, service and agent verbs, and the API doors) refuses an instance of that name that is a workspace, a template or a copy of one, naming what it is and what frees the name ("Project acme-fix cannot take instance acme-fix: it is workspace fix of project acme. Delete the workspace (sudo sail project workspace delete acme fix) or give the project another name; the workspace itself is reached with sail project workspace shell acme fix."). So do a terminal open (asking Incus of that one instance by name, within 3 s, outside the terminal host's lock, and refused saying so when Incus does not answer; an attach and a ticket ask Incus nothing), `skills ls`, and every API door that reaches a container by a project's name (`409 conflict`, with the remedy). `POST /v1/projects` refuses such a name on a box that holds the instance, as `project create` does, each asking Incus of the one name within 3 s; a box that holds none cannot know, and a project of that name that reaches by sync a box that does is said there once, in the round that brings it, and never given the instance (its resources are not applied to the workspace). `project destroy`, `stop` and `switch` read Incus for real in a dry run, so `--dry-run` names every workspace and the template the real run removes. A copy of a workspace made by hand is not Sail's: it outlives its project, and the round that drops the project says once that it was kept.
- **An event stream that opens with nothing to send asks its door once, as it opens.** Its first page is read for the request that was just admitted, so no second check follows the `: subscribed` comment; every later page is still asked before it is read and again before it is written. `OpenStreamRecheckTest` had counted that second check on a slow macOS runner when it landed after the test began counting.
- **A client that was away asks for exactly what changed since the last thing it saw, and gets it in order with no gap.** `GET /v1/changes?since=<position>[&types=spec,room,message][&limit=n]` answers the specs, rooms and messages the caller may read now whose newest revision is after the position, in order, each once a page as it is now: `{seq, type, id, row}`, or `gone` or `erased`, with no content, for a row filed where the caller may read. A row carries what its own record holds, shaped as its list route shapes it less the fields that list derives from other rows (a room's specs, latest activity and open question; a spec's room wake, seated agent, latest activity and open question), which a client derives from the rows it holds; a change to one row never re-sends another. A page holds at most 500 rows' changes (100 by default), with `next` and `more`. A position is one opaque string naming the database, the change log's `seq` and the entry standing there; it survives a restart. Every list and detail read of a spec, room or message answers a `Seq` header: the position it was read at, so "read, then follow the feed from it" misses nothing. On `GET /v1/events/stream` a row change is `event: change` with `id: <position>`; a stream that sends `Last-Event-ID` (or `?after=`) is first sent every change since, a page at a time between whatever else it sends, then live ones, a change committed during the replay included. A stream reads the feed when this process commits, or when another process wakes it with `POST /v1/changes:wake`, which any authenticated caller may send, which carries nothing, which no client is ever sent, and which wakes no one when nothing was written since the last; every command that writes the box's database now sends it after its commits. No other event makes a stream read; an idle stream reads nothing. Each page is read as its caller is now and sent only if the caller is still admitted once it is read. A position that does not parse (an older client's number), names another database, stands on an entry no longer there (a restored database; an entry erased since), or is from before a change of what its reader may read is `409 resync_required` and one `event: resync` with an `id:`, each naming the newest position; a stream told so after it started is then ended. A change of what a reader may read is: a spec, room or run moving between projects (for readers of both), and a person's grants, restrictions or removal (theirs). The deletion or erasure of a message filed apart from its conversation (every message said in a room before it moved, and any later reply in one of its threads) resyncs the scoped readers of the project it is filed under, though they can read none of it. A reader that hears only a room's steering voices (an agent) is never told the erasure of a message, and keeps one it was told. Two consequences for a mixed fleet: a row stripped on one box reaches a 0.46.5 box, where a dropped `stages[].skill` means that box judges under `sail-review` until it upgrades; and a row with a deleted key that syncs to an upgraded box before that box's own migrate ran is unreadable until it runs, a window `sail upgrade` closes, not a steady state. A 0.46.5 box reading a definition with `stages[].brief` or `repos[].forge` ignores both.
  - **`gh` is logged in.** Where provisioning or `project apply` writes a token into `~/.git-credentials` for a GitHub host (`github.com`, or a repo marked `repos[].forge: github` for a GitHub Enterprise host), it also logs the installed `gh` in for that host as the dev user, the token pushed to a `0600` file under the dev home and consumed on stdin by one command that removes it, success or not; a failed login fails the step naming the host. The room lane's read-deny rules now also cover `~/.config/gh/**`. A run on a repo whose forge has no authenticated CLI in the container is told to say so in the room instead of claiming CI green.
  - Provisioning phase `CONTEXT_GENERATED` is now `SKILLS_INSTALLED`; a box whose provisioning state file names the old phase resumes from the start of provisioning.

## 0.46.5

- **The journal decides every local write, so no door can forget.** Who may write a synced row was one rule per type, which each door had to remember to ask; an audit found nine doors that did not, and two that answered a rule's refusal with a code of their own. Every write that is not a push is now decided where its revision is recorded (`RevisionJournal`, and `MessageStore.append` for a post), a pushed one at main's commit as before, each exactly once. Doors keep only the admission that precedes a side effect.
  - **Doors that were unchecked are now decided by their type's rule.** `sail project apply`, `project edit`, the `project add-`/`remove-`/`resources` edits and `sail project files add` on a node whose FDE is a viewer are refused (`read_only_credential`: "Your credential is read-only and cannot change projects." / "… change files."), before a command clones, starts or ingests anything. `sail agent run` and `sail agent sweep` there are refused the same way, with no run reserved and no agent launched. A conflict resolved with `--mine` or `--merge` is an edit of the row, decided by its rule against main's version: a merge that sets another assignee is `forbidden_admin_only`, and an agent resolves only what its FDE may edit. `--theirs` only adopts main's version and decides no row, but it gives up what the box parked, so a read-only credential is refused it (`read_only_credential`); any credential that can write may. The door's own "Only this node's owner or an admin can resolve its conflicts." (`forbidden`) is gone.
  - **Renaming a project is admin-only**, on a node and at main's commit: it moves every spec and file in the project, whoever's they are. A member's `sail project rename` is refused before its container is stopped or anything is written (`forbidden_admin_only`: "Renaming project '<name>' moves every spec and file in it, whoever's they are, and is an admin-only action."), where it used to re-journal other members' specs that main then denied.
  - **A run is created only for the owner of the spec or room it names**, by an admin, or — naming neither — for the FDE it acts for, on every lane and at main's commit. A node can no longer push a run onto another FDE's spec (denied: "Run <id> belongs to spec '<spec>', owned by '<owner>', not you."). A run names a spec or a spec-less room, never both, as every launcher has always written it: one naming both is refused for everyone (`invalid_request`: "Run '<id>' names both spec '<spec>' and room '<room>', and a run works one."), so a run on the pusher's own spec cannot be pushed into another member's room, where it would have silenced that room's wake. A run that reaches main ahead of a spec or room its own box made lands as before. A spec an admin reassigns while another FDE's box is running it keeps the run it has; the next run that box starts on it is denied on its push. A credential naming another FDE can no longer start an ad-hoc run on a box that is not its own (`forbidden_not_assignee`).
  - **One code per refusal kind at every door.** Over HTTP a read-only credential's write was `forbidden` ("Your role is not permitted to perform this action.") from a route tier that ran before any rule; it is now the rule's `read_only_credential` with the rule's message and fix, as on the socket and the host CLI. HTTP tiers a route for read, and for admin where it administers the control plane, never for write: `POST /v1/sync` with no `main` and `POST /v1/projects/{p}/agent/report` are now served to a read-only credential, as `sail sync` and `sail agent report` are on its box; restoring or deleting a snapshot is refused it (`read_only_credential`). Managing a spec-less room you do not own was `not_your_spec` from the membership door and is now the room rule's `forbidden_not_assignee` ("Room '<id>' belongs to '<owner>', not you."), the code deleting it already gave; a room that belongs to another box is still `not_your_spec`. Kinds map to codes in one place: `READ_ONLY` → `read_only_credential`, `NOT_OWNER` → `forbidden_not_assignee`, `ADMIN_ONLY` → `forbidden_admin_only`, `NOT_AUTHOR` → `forbidden_not_author`, `FIXED` → `invalid_request`, `NOT_PRUNABLE` → `spec_not_prunable`, `NOT_PUBLISHABLE` → `forbidden`.
  - **A spec may be born over a room that is already its owner's.** `POST /v1/specs` with the id of an existing room was `conflict` (409) for everyone, while main's commit took the same birth from a node. The spec rule now decides it at the door as on main: the room's owner, or an admin, creates the spec, which adopts that room as its own and mints none; anyone else gets `forbidden_not_assignee` ("Room '<id>' already exists, and a spec's id is reserved for its own room."), and so does everyone, on a node and at main's commit, for a spec with that id born in another room (`room_id`), which would have left the room answering as the other one. A room of another project is `invalid_request`. Creating a spec whose id is already a spec's is now `conflict` (409, "Spec '<id>' already exists."), where it was an `internal` 500.
  - **An operation that writes several rows commits them once.** A spec update (its row, its wake, and the findings a move into or out of `done` resolves), a delete (with the shipped follow-up catch-up that used to run before it), a follow-up (the draft, its body, and its links to the findings it was drafted from) and a dispatch or restart (the run's reservation, the reset to `pending`, the claim and the superseded reviews) each used to commit in up to four transactions; a refusal or failure of a later row left the earlier ones. A refused write now rolls back everything its operation wrote, even where a caller swallowed the error.
  - **Refusals read in a new order where a rule used to run first.** A write is validated, then decided as it is recorded, so a request that is both invalid and not permitted now answers the validation: a read-only session creating a spec in a room that does not exist gets `room_not_found` (it was `read_only_credential`), restoring a revision that does not exist gets `invalid_request` whoever asks, deleting a room that still holds specs gets `conflict` before the owner check, and approving a review with no human stage waiting gets `invalid_request`. Nothing a credential could not already read is disclosed.
  - **The socket answers a refusal in HTTP's envelope.** An error thrown on the in-container socket was `{"error": "<message>"}`; it is now `{"schema_version": 1, "error": {"code", "message", "action", "field_errors"}}`, as HTTP's. Route, method and credential problems on the socket keep the short form.
  - A project purge's handling of unfinished runs is the erase rule's (`EraseAuthority.idle`), asked by the local prune and by main's decision on a node's request, where each kept its own copy. Behaviour is unchanged: a project is purged whole once its container is gone, its runs with it.

## 0.46.4

- **A project says how each stage works; sail still runs the loop.** What a build, a reviewer and a fix agent are told about how to do their work used to be three hard-coded strings, each mixing advice a project may want to change ("Only report genuine issues") with contracts the loop parses or enforces ("Respond with exactly one JSON object", "push the branch and open a pull request"). The instructions of each stage are now a skill, a folder with a `SKILL.md` and optional scripts and reference files, that sail ships a default for and a project can replace.
  - Sail ships `sail-build`, `sail-review` and `sail-fix`. A project that configures nothing gets them, and every sentence of the three prompts is still said, in the default skill or after it: each prompt gains a `## How to do this work (skill: <name>)` section, and two sentences are split around it (the build's "When complete, run the full local verification …, commit …, push the branch, and open a pull request" and the fix agent's "When every finding is addressed: run the project's verification locally, commit …"). The reviewer's rules 1–4 moved into `sail-review`; rules 5 and 6 are now 1 and 2.
  - A project's skill is project files under `.sail/skills/<name>/` (`sail project files add <file> --as .sail/skills/<name>/SKILL.md`), synced and limited like any project file and never copied into the workspace. Three keys name which skill a stage uses: `agent.build_skill`, `agent.review_pipeline.fix_skill` and `agent.review_pipeline.stages[].skill`. A key accepts its own default or a project skill's name; a name that is not `[a-z0-9][a-z0-9-]{0,63}`, another name starting `sail-`, `spec`, `spec-board`, `verify`, one of the project's `agent_context.rules` names, or a `skill` on a human stage is refused when the definition is read, naming the key. That holds for the defaults too: a rule named `sail-build`, or `sail-review` or `sail-fix` in a project whose pipeline runs them (no `review_pipeline`, or one with no stages), is refused. A `review_pipeline` block with a `fix_skill` and no stages runs the default stages and keeps that skill. A box on an older sail ignores the three keys and runs the defaults.
  - Sail puts the skill's body in the prompt itself on every launch and both harnesses, and what the loop parses or enforces follows it, so no skill replaces the verdict envelope, the push and pull request, or the dispute lane. The skill's folder is installed where the harness looks for skills (`~/.claude/skills/<name>/`, `~/.agents/skills/<name>/`) before the agent starts: stamped with a fingerprint of its files, not pushed again while it is unchanged, and replaced whole, in one step, when it changed. Launches that replace one folder at once take turns (`flock` on the skills directory), and a skill is built beside the skills directory, never in it, in a hidden `.sail-stage-build-<name>.<runId>` folder that no skill or rule can be named like; one a dead launch left is removed by the next install of that skill once it is a day old. A skill is read at each launch and bounded (a body of at most 32,000 code points, a folder of at most 32 files and 1 MiB). One that cannot be read stops its stage: a dispatch is refused with `bad_request` naming `.sail/skills/<name>/SKILL.md` before anything is reserved, a reviewer's review errors and is retried within the errored-review budget, a fix agent's review escalates.
  - **`sail project skills [-p <project>] [--json]`** lists the build, each agent review stage and the fix with the skill each runs under and how it stands (`built-in`, `project (n files)`, `missing`, `invalid: …`); **`sail project skills show <name>`** prints a skill's `SKILL.md`, so a project starts its own from sail's default.
  - A dispatch for an agent sail does not know is now `bad_request` before the spec is claimed, where it was `agent_launch_failed` after; a spec with no `agent` in a project with no `agent.type` is refused the same way ("Project '<name>' names no agent; set agent.type or the spec's agent."). The provisioner's "files/ directory is empty" notice also shows for a project whose only files are skills.
- **What runs a project reads it from the catalog, never from a file.** The review loop, every API lane (dispatch, ad-hoc runs, room wakes, reviewer and fix launches, watcher relaunches, stops, snapshots, membership), Slack and webhook notifications, and `sail agent watch`, `status`, `report`, `attach`, `context regen` and `run` read a project's definition from its catalog row (`projects.definition`), where they used to read `~/.sail/projects/<name>/sail.yaml`. The file is still written, as a copy nothing running reads.
  - A project revision that arrives by sync, or that `project apply` records when it creates the project, `project edit` or a mutation command records, is what the next dispatch, the next loop event and the next notification use, with no `sail project apply` run; a box that already had the project used to keep its old file until someone ran `project apply`. A review in flight whose stages no longer match escalates as before. A watcher already running keeps the notifications it started with. A `sail.yaml` edited by hand, with the row unchanged, is read by nothing that runs the project.
  - A project with a file and no row is not found: a dispatch is refused with `Project '<name>' is not in the catalog.` and the fix (`sudo sail migrate` imports a descriptor that is on the box; `sail project apply -f <file>` creates the project). No row is ever substituted by a file. A row that cannot be read fails naming the project: a lane with `project_load_failed`, a running review by escalating ("The definition of project '<name>' in the catalog could not be read: …; fix the project's definition with `sail project edit`, then re-dispatch with --restart"), and notifications with a warning and nothing sent. `agent status` and `agent attach` still go on without a definition for a project with no row.
  - A definition that does not reach the catalog is not written to the file either: `project apply -f` creating a project, `project edit`, `project add-repo`, `add-service`, `remove-service` and `resources set` now exit non-zero naming the project and the cause where they printed a note and went on. `project add-repo` has already cloned the repo into the container when it records, and `add-service` and `remove-service` have already changed the container's services, as before.
  - `agent context regen` and `agent run` write the box's git identity into the agent's context from the row: `${GIT_NAME}` and `${GIT_EMAIL}` are replaced where the box has a git identity and left in place where it has none, which no longer fails the command; on the box that authored a project the context used to name what was typed into the file. A git name with an apostrophe (`O'Neil`) is written as it is: the identity is substituted into the parsed definition, never into the row's text, where the quoted placeholder made the substituted text unparseable, on this path and when a project is provisioned.
  - `-f/--file` on `spec dispatch`, `agent sweep`, `agent run`, `agent watch`, `agent status`, `agent report`, `agent attach` and `agent context regen` is accepted and ignored: the project is read from the catalog. The spawned watcher no longer receives it. The `project` commands keep theirs.
- **Every agent run launches, is watched and stops one way, and each lane's limits are the project's.** A reviewer and a fix agent used to run as a foreground `incus exec` the server blocked on, bounded by a 30-minute limit no setting changed. At the limit only the host side of the exec was killed: the agent kept running in the container, the review loop recorded a failure, and the agent then pushed its work into a loop that had stopped listening. Four specs in two weeks needed a manual takeover for it.
  - A reviewer and a fix agent are now runs like a build: each invocation is its own run row (role `review` or the new `fix`) that names the review it serves (`review_id`), launched as its own `sail-agent-<runId>` systemd unit with the same hooks and environment, watched by its own `sail agent watch`, and ended by the one authoritative `agent_session_stopped`. The review pipeline no longer waits on an agent: it routes each stop by the lane of the run that stopped. A build's stop starts the review; a reviewer's resolves its stage from the findings in that run's own log; a fix agent's commits what it left and starts the re-review.
  - **`agent.review_pipeline.guardrails`** (`max_duration`, `max_idle`, `action`) bounds reviewers and fix agents, default `45m` / `20m` / `stop`. `agent.guardrails` keeps bounding builds, ad-hoc runs and chat turns, default `4h` / `20m` / `stop`. Both blocks parse the same way, and an invalid duration, a zero limit, an unknown action or a `guardrails:` value that is not a block is now refused when `sail.yaml` is read, naming the block, the key, the file and the accepted forms, where an invalid duration used to surface only when a run launched or its watcher started. A block that names only some keys sets only those: `max_idle` left out of a block is no stall limit. The watcher takes its run's limits on its command line (`--max-duration`, `--max-idle`, `--action`), so an edit applies to the next run; a watcher re-armed after its own death takes the limits as they are then.
  - **The watcher publishes the stop it causes.** On a trip it kills the unit's whole cgroup in the container and, once the container answers that the unit is gone, records the trigger beside the run (`~/.sail/runs/<runId>/guardrail-triggered.yaml`, no longer one `/home/dev/guardrail-triggered.yaml` per container) and publishes the run's stop with `reason` (`time limit (45m)`, `stall (20m)`). A unit that survives is killed again at the next poll and never reported ended, and no kill is tried while the container cannot say whether it worked, so an agent that ends before one was tried is reported as the plain exit it was; a watcher that finds its container stopped, or its unit's manager and process gone, ends without a stop and leaves the run to the reconciler. This holds for builds too, where the stop used to come from the reconciler's next sweep with no reason. A stop that carries a `reason` carries no `exit_code`: a killed run has none of its own. A build ended this way still goes to review, as before. The trigger file gains `cause`, the reason as the stop says it.
  - **The watcher notices an exit on the clock and survives a daemon restart.** It asks the container whether its unit is still active at least every 15 seconds, where it used to ask only after 15 seconds with no event from any run in the project. When its event stream ends with a daemon restart it subscribes again at its next poll, and the stall window starts afresh: a watcher that outlived a restart used to go deaf and kill a working agent for a stall one `max_idle` later.
  - **The missed-stop reconciler leaves a run to its watcher.** It publishes no stop for a run while a `sail agent watch` process for it is running, so a sweep landing between a watcher's kill and its stop, or before its next poll, no longer gets in first with a stop that names no exit code and no reason. For a run no watcher covers it says what is still known: the non-zero exit code a failed unit holds, and the limit the watcher recorded beside the run when its stop never reached the daemon.
  - **A reaped agent is dead, and the room says why.** A killed reviewer errors its review (`review_errored`: `reviewer killed: time limit (45m)`) and is retried within the same budget as any errored review. A killed or failed fix agent publishes `review_iteration_failed` (`fix agent killed: stall (20m)`, `fix agent failed: exit 1`), nothing of its is committed, and the review escalates. `review_iteration_failed` is now narrated in Slack and in Mast's room, where it used to be shown nowhere.
  - **The fix agent no longer waits for CI.** Its task ends at a pushed commit ("verify locally, commit, push, end your turn; do not watch CI"), and the stop gate asks a fix agent for a clean, pushed tree only. The re-review judges the branch, and the pull request shows its checks to whoever merges. This is what makes 45 minutes a real budget for a fix that runs full verification. A build is still asked to watch its checks to green. A reviewer is never blocked at its stop: its last message is the verdict the pipeline parses.
  - **A daemon restart fails nothing.** The server no longer marks running reviews failed at start. A reviewer or fix agent that is still running has its watcher re-armed; one that ended while the server was down has its stop published by the missed-stop reconciler, which reconciles them as it does builds; and a review left `running` with nothing running it goes on from its stage rows.
  - **`review.log` is retired.** Every run's log is `~/.sail/runs/<runId>/agent.log`, whatever its lane, and `GET /v1/runs/{id}/log` and `/stream` read it the same way. `sail agent log --review` shows the latest reviewer run's log, and the new `--fix` the latest fix run's. `sail agent log`, `status`, `report` and `attach` with no flag read the newest run of any lane. A review that ran before this release keeps its log: its run recorded `~/.sail/runs/<id>/review.log`, and the log endpoints and `sail agent log --review` still read that file for it.
  - A reviewer and a fix agent reserve their spec's repos through the same gate as a dispatch, so neither starts beside a live build of its own spec, a full chat turn or another spec's run over the same repos; a claim refused for a run in the way makes the review wait, with no attempt spent and nothing escalated. **The wait is recorded**: the review names the run that holds its claim (`reviews.waiting_on`, local to the box and never synced), the stage it could not start stays `pending` (it used to read `running` with no reviewer, and main announced `review_stage_started` for it), and the room is told in the same write, so once per run waited on: "Review is waiting for run `<runId>` (`<role>` of `<specId>`) to finish." The holder's stop launches the waiting step; a holder that ends with no stop is rescued by the reconciler once its row has been terminal for longer than the launch grace (2 minutes), exactly once per (review, holder). The reconciler no longer samples the dispatch gate or retries a rescue up to three times: a review refused three times running by runs that end silently is launched after the third, where it used to be stranded, and a review no replay can move is no longer replayed four times. A container held by a snapshot restore is still an error. A review no longer holds the whole container: a spec on other repos can be dispatched while it runs.
  - A launch that reports failure after its agent started no longer escalates the review while that agent works on: the run stands, and the loop waits for its stop. A launch whose run was finished under it tears its agent down unless the agent is verified gone.
  - The loop acts only on a spec still `in_progress` or `review`: a spec cancelled while its reviewer runs gets no fix agent. A build's late or replayed stop after an escalation starts no new review, and the stop of a build a re-dispatch has replaced starts none beside the new build. A box counts only its own runs as serving a review, and moves unasked only the loops whose newest run it executed.
  - Upgrade with no review loop in flight: a reviewer an older server started is not a unit this release can watch or stop, so its review is retried from its rows while that reviewer may still be running. A fix agent an older server started is ended first: such a server exported the review id as `SAIL_RUN_ID`, and before a fix run's unit starts sail kills every process in the container whose environment holds exactly `SAIL_RUN_ID=<reviewId>`, so two fix agents never work one branch. A run this release starts exports its own run id and is never matched.
  - **Every review ends.** A failed gate whose findings a person resolved before the fix agent launched is reviewed again as the next iteration, where it used to stay `failed` with its spec in `review`. A review whose project no longer has a pipeline with stages escalates saying so ("the project's review pipeline has no stages; set agent.review_pipeline.stages, then re-dispatch with --restart"), where it used to stay `running`; so does one whose stage was renamed, removed or retyped in `sail.yaml` while it ran ("the project's review pipeline changed while this review ran: stage '<name>' is no longer where the review has it"), where a reviewer's stop used to leave it `running` with nothing owed; a retry of an errored review and the re-review after a fix are checked the same way, since findings carry forward by stage name. A `sail.yaml` that is there and cannot be read is an error naming the project, never taken for a project with no pipeline, and a review that finds it escalates saying so, as does the review of a build that ends while it cannot be read; the descriptor the server reads is now replaced in one move by every command that writes it for its project (`project init`, `edit`, `apply`, `rename`, the `add-`/`remove-`/`resources` edits, and sync), so nothing reads half of one; a file named with `-f` is still written in place, also when it names that same file. An escalation closes any stage still `running`. A review's end is one transaction: its final status, the reason, its spec's status and the room line commit together or not at all, so a daemon death no longer leaves a passed review beside a spec still in `review`; a person's approval through `POST /v1/reviews/{id}/approve` is one transaction too (the stage that waited on them, the review and its spec), and moves the spec only if it is still in the loop's hands, where it used to move a cancelled spec to `awaiting_merge`. An escalation is now also a room line ("Review escalated: <reason>."). A verdict or reason longer than a room message holds (64 KiB) is cut in the room and marked as cut, and kept whole on the review.
  - **The escalation reason syncs.** An escalated review records why in `reviews.error`, which rides its synced row, so main's `review_escalated` carries the same `detail` the driving box published. A stop the reconciler publishes for a run whose stop was already said carries `replay: true`: the pipeline routes it, and Slack and webhooks no longer say "Agent stopped" a second time. A run's first stop is always said, however long ago its row ended. Main no longer says "stage failed" for a stage that was closed for an error, which the driving box never said: the review's error or escalation tells it on both.
  - **A tool call in flight is not a stall.** The watcher counts its run's tool calls that started and have not finished; while one is in flight and a `max_duration` bounds the run there is no stall deadline, and the stall window starts again when the last one finishes. A call that failed counts as finished: Claude Code reports a failed call (a command that exits non-zero) through `PostToolUseFailure`, never `PostToolUse`, and sail's hooks now publish `agent_tool_finished` from both. A call Claude Code denies fires neither, and a finish can be lost on its way to the daemon, so the count is also set to none whenever the main agent's batch of calls resolves: the new `PostToolBatch` hook publishes `agent_tool_finished` with `batch: true` (a subagent's batches publish nothing). A call that began where the watcher could not hear it, before a re-armed watcher started or while its event stream was down, is not counted and gets one stall window from then. Codex has no batch hook, so there a lost finish leaves `max_duration` as the bound. A reviewer or fix agent whose one verification command runs past `max_idle` (20m by default) is no longer killed while working. With no `max_duration` set, `max_idle` still bounds a tool call that never returns.
  - **`sail agent watch --started-at <instant>`** is required: whoever spawns or re-arms a watcher hands it the run row's `started_at`, which anchors `max_duration`. The watcher no longer reads `started_at` from the run's session file in the container, which the agent can write.
  - **A kill reports what it did.** Halting an agent answers one of three outcomes: `Ended` (a signal was delivered and the container answered that the unit is gone), `Survived` (both signals were sent and the unit still answers active) or `Unanswered` (the signal could not be delivered, or the unit's manager did not answer afterwards). A foreground session with no unit is halted by its pid file in one script in the container, and only what that script prints (`gone` or `alive`) is believed: a pid file that could not be read, a signal that could not be delivered or an exec that returned no answer is `Unanswered`. The unit is reset and the run's pid file removed only on `Ended`. The watcher counts a kill as tried only on `Ended` or `Survived`, so an agent no signal reached that then exits 0 is reported as the clean exit it was, with its exit code and no reason, where a fix agent's finished work used to be dropped and its review escalated. `sail agent stop` finalizes only on `Ended`: a manager that does not answer fails the stop with `agent_stop_failed` and leaves the run `stopping` for a retry, where it used to be finalized `stopped` over a possibly live agent. Whether there is an agent to stop at all is asked the same way everywhere: an agent is gone only when one script in its container looked for the run's process and printed that it is gone, or incus lists the container stopped or absent, so no number of lost commands reads a live agent as gone. A container that runs no command fails the stop with `agent_status_failed` and writes nothing, where every command failing used to read as "no agent running" and the run was recorded `stopped`; the reconciler, the watcher and a failed launch's cleanup treat that container as still running its agent and ask again. A launch whose run was ended under it says whether its agent was torn down, survived the halt or could not be confirmed stopped. A watcher now also ends when its run's authoritative stop or cancel is published by anyone, where one watching a unit whose manager was gone for good used to poll every 15 seconds until the container restarted.
  - `sail project init` writes the whole `agent` block: `guardrails.max_idle` and `review_pipeline` used to be dropped. A review limit left at its default (`max_iterations`, `max_finding_age`, `review_pipeline.guardrails`) is no longer written when `sail.yaml` is rewritten, so `project add-repo`, `add-service` and `resources set` no longer pin a project to the defaults of the release that rewrote it. Written YAML indents a list's items under their key and never folds a long value onto a second line.
  - Upgrade note: between the binary swap and the `sail-api` restart, a watcher spawned by the old server lacks `--started-at` and exits; the new server's re-arm pass at start covers that run.
  - The watcher addresses a stop to the run named on its own command line, never to one read back from the run's session file, which the agent can write. A run that died before its watcher attached (a missing CLI, a bad flag) ends by a stop carrying its exit code, where it used to be reconciled minutes later as a clean finish.
  - `sail agent stop` now stops a reviewer or a fix run, which it used to refuse (`invalid_role`). It does not cancel the spec; the review escalates, so the loop does not retry over a person's stop. The stop marks the run as the operator's (`runs.stop_source`), so the watcher's own stop of the halted unit escalates too, whichever is heard first, and never restarts the loop; a stop that lands while the reviewer is still launching escalates as well. A build an operator stopped whose spec was not theirs to cancel starts no review. A `sail agent stop` whose halt fails gives the run back only when the agent is verified still running; over an agent that is gone or cannot be probed the stop stays claimed, for a retry or the reconciler to finalize. `GET /v1/runs` shows `review_id` on reviewer and fix runs.
  - A stop the missed-stop reconciler replays carries the reason the watcher recorded when it killed the run. A fix agent killed for a limit just before a daemon restart is still a failed iteration afterwards, and nothing it left is committed.
  - No further floor change: the `fix` role, `review_id` and `stop_source` ride the 0.46.4 floor above. The `runs` table is rebuilt to admit them, and a review run recorded before this release names the review it ran under.

- **An event drives only what its sender may drive.** `POST /v1/events` used to publish any event a writer sent, and this box's machinery acts on every event as itself. A member could move another member's spec to review and start its review with a forged `agent_session_stopped`, finish a run that was still running, fake the evidence the missed-stop reconciler reads so a stranded spec was never rescued, use up a room's commit guard, and send Slack and webhook notifications for work that never happened; a future `ts` held the reconciler off, and `agent` named whoever the sender liked.
  - One rule in sail-core (`EventAuthority`) decides which events a client may publish, at both doors. It is deny by default: a type it does not list is the server's own, emitted after the write it describes, and is refused from everyone.
  - What a box did and observed is its own FDE's to report, which is how the host CLI and the watcher speak, or an admin's. Anyone else only retells what another box did (`source: sync`), as main's sync server does for the FDE who pushed, and only about a spec or room they own: a retold event starts no review and finishes no run, and a run a node pushed is no key to the spec it names.
  - A run's own principal publishes only its four hook types, and only for its own run; the socket's separate allowlist is gone.
  - `snapshot_created` and `board_updated` speak for the box: an admin or the box's FDE. A `spec_message_posted` announcement names a message and nothing more; the server decides it on the conversation the message is in, rebuilds the event from the message it holds, and refuses one it does not hold.
  - The server stamps what it knows: its own clock as `ts`, the project and conversation of the run, spec or room the event names, and the publisher (handle, role, lane) it authenticated, stored with the event and served as `publisher` on the stream and in history. `agent` is a label, no longer who published.
  - A refusal is a 403 naming the event type and what the sender may not drive; a refused event never reaches the bus.
  - A relayed `agent_failed` names its run, as its stop does.
  - A member who runs `sail spec dispatch`, `sail agent run` or `sail agent stop` through main's SSH gateway publishes as themselves, not as main's FDE, so the events those commands and their watcher publish (`spec_dispatched`, `snapshot_created`, `agent_session_started`, `agent_cancelled`, the watcher's `agent_session_stopped`) are refused: the dispatch itself still lands, but Mast's timeline and Slack show no dispatch row for it, and the spec moves to review and its review starts when the missed-stop reconciler's next sweep finishes the run, not when the agent exits.
  - A spec an admin reassigns while another FDE's box is still running it loses that run's relayed stop on main: the rule holds a run another box executed to the owner of the spec it works, and that owner is no longer the FDE who pushed it. The run still finishes on its own box; main records nothing of it (no event, no timeline row, no Slack line), and since that box's move of the spec to review is denied on the sync lane for the same reason, the spec stays `in_progress` on both boxes until an admin moves it.
  - Mast shows the publisher the server stamped. An event stored before this release, or one the server emitted itself, has none and shows its `agent` as before.
  - No floor change: events never cross the sync wire. The `events` table gains a `publisher` column.

- **A box remembers which version of a shared file it wrote.** Whether a copy on disk was this box's output or a person's edit used to be decided from the file's change history, which compaction trims to the newest twenty revisions, or by comparing the copy with the current row, which on main is often newer than the copy. After enough pushes from nodes, main took its own copy for a person's edit: `files pull` kept it, `files add` and the API's put skipped it, and `sail project up` put the stale copy in the container; a hand revert to an earlier retained version was overwritten; and every upgrade's import republished main's stale copies over the fleet's newer versions and brought back files a node had deleted.
  - Each box now records, box-locally and never synced, the content and mode of every shared-file copy it writes to disk or publishes, and decides from that record alone: a copy that matches it is this box's, refreshed or removed as the fleet's version moves; a copy that holds the current version is in sync whatever its provenance and this box's from then on; any other copy is a person's, kept and reported. A write records the version before it moves the file into place and again once it has, and a publish records what it published for the materialize that follows, so a write that dies in between, or a publish whose materialize never ran, leaves a copy this box still knows as its own.
  - The upgrade's import publishes only a person's copy, never this box's stale output, and leaves a deleted file's copy for the materializer to remove; what it publishes it records, so no later upgrade publishes it again.
  - The upgrade seeds the record once from the history the box still holds, superseded and deleted versions included. A copy matching no retained version may be your unpublished edit or a version this box wrote that compaction has dropped — on main, mostly the latter — and nothing left can tell which, so it is recorded as undecided: kept, reported with the remedy, and never published, until a version this box writes lands in its place (delete to take main's, or capture with `sail project files add` if yours). The one edit history can still tell, an execute bit a legacy copy was given that no version had, is left for the import to publish. A copy the upgrade cannot read fails it before its completion marker, with what it seeded kept, so the import never publishes that copy as a person's edit once it is readable; `sail migrate` reruns to finish.
  - The seed reads this box's own files, so only `sail migrate` and the server run it; the sync lane, which converges the shared database as the `sail` user, leaves it to them.
  - The record goes with a file's erasure, moves with a project rename, and leaves with the copy it describes.

- **A review's findings sync with it, so every box holds the same review.** Findings used to live only on the box that ran the review, with the synced review carrying counts; a review denied after its spec was reassigned lost them, a node that kept them held a review main never had, and a follow-up's links to them vanished when its spec was deleted.
  - Every stage's findings — each field, resolution, evidence, what it was carried from, and the follow-up spec drafted from it — are the review's content, hashed into its snapshot and stored once in the blob store like a spec's body. Main, every node and Mast read the same findings; the API's shape for reviews and findings is unchanged.
  - Adding, resolving, disputing and carrying findings into the next iteration each write one revision of the review, decided by the review rule like any other write. A node adopting main's review takes main's findings exactly; a review main never took is withdrawn with its findings kept in the change log and announced.
  - A finding names the follow-up spec drafted from it in that content, so the link survives the follow-up's delete and restore on every box, and marking the follow-up `done` fixes the finding in the same content — written by main, when the follow-up is marked done there or when a node's change reaches it — a resolution that outlives the follow-up's archive and erasure. Findings two boxes changed at once merge finding by finding, so main fixing one while its owner's review rules on another parks no conflict. A finding names one follow-up, the latest drafted from it; the upgrade keeps the latest of several earlier links. The box-local `spec_source_findings` table is gone, and so is the unused `spec_attachments` table.
  - A reviewer's finding always gets an id this box mints, so two reviews can never claim one finding row, and a review's content may only write its own rows: a stage or finding another review holds is refused with the reason, never written over.
  - Every control character in a synced snapshot or content document is escaped on the wire, where a C1 character in a finding's text used to make every other box refuse the review for good.
  - The upgrade leaves a review whose spec main pruned — held here only until its own erasure pages in — unfolded and reported, instead of failing the whole upgrade on it.
  - The upgrade folds each box's existing finding rows into one revision per review, which a node's next sync pushes; if the spec is no longer that box's FDE's, main denies it and the node keeps the revision in its change log.
  - The fleet floor is 0.46.4: an older node would push a review back without its findings.
- **The review loop decides in one place and acts in one place.** Every step from a build's stop to `awaiting_merge` is one row of one pure function (`LoopDecision.next`, tabled in ARCHITECTURE.md under "The loop machine") that `LoopSteps` carries out. What the loop does for a stop is unchanged, with three exceptions: a review a re-dispatch replaced while one of its steps ran (a reviewer's log being read, a launch, a fix agent's leftovers being committed) is left alone where that step used to finish on it, nothing more is started or escalated for a spec someone moved out of the loop while a step ran (no next reviewer, no person's stage, no fix agent after a failed gate, no escalation of a fix whose leftovers could not be committed), and a failed fix iteration is announced (`review_iteration_failed`) once its review's end is written, not before. The server's event bus now shuts down without waiting out a 200 ms poll per subscriber.
- **Adding a coding harness is adding one adapter.** Everything that differs between Claude Code and Codex now sits behind one interface, `Harness`, with one adapter each and a registry, `Harnesses`, that names the default once; the two hook files are rendered from each adapter's declaration of which events run which of sail's hooks. Every launch command and both hook files are the same text as before. Two texts a person reads change: `project init` offers only the harnesses sail knows, where it used to name one that does not exist, and the warning for a dropped `reasoning_effort` no longer ends "Only Codex honors reasoning_effort.".

## 0.46.3

- **Every offer settles, and no round fails for something that will arrive.** One rule in sail-core (`Decidability`) decides what an offer depends on, whether main holds it, and what becomes of an offer whose dependency can never arrive. Main's refusal, the node's hold-back and the node's settlement all read it; the per-store hold-back SQL is gone.
  - Main refuses a push (and the node holds it back) only while a dependency has not arrived yet — a born-in spec's room, a message's conversation and the run of its agent author, an agent revision's run, a review's spec — so it lands the round the dependency does, never failing the round. A review of a spec main does not hold is refused and awaited, where it used to be denied "which has no owner" and deleted.
  - A dependency main has erased is terminal: main denies the offer and marks it `gone`, and the node settles it the same round instead of offering it forever. `RoomStore.holdsConversation` no longer counts an erasure as holding the room.
  - The node settles what can never be decided: a born-in spec whose room is gone (deleted before its first sync, denied, or erased) is re-homed into its own identity room; anything else is withdrawn as a denial is, kept in the change log. A spec an erased run's agent edited reverts to main's version once the run's denial settles.
  - **Runs sync first.** The registry syncs runs before anything their principals wrote, so an agent's run lands before its spec, post, review or file, in one round.
  - **No single offer fails a push or a session.** Main answers each offer in a push on its own: an exception inside one commit is that offer's refusal, and the offers beside it keep their answers. The node settles a refusal per offer — the refused row is left and offered again next round, every other answer applied — so one refused offer never fails the type or the session.
  - **A file above main's `limits.file_max` never breaks the channel.** The welcome carries main's limit; the node enforces the lower of its own and main's at every ingest, and a file row already above it is settled once rather than refused mid-upload every round: withdrawn, or reverted to the version main holds, after main has been asked whether it took it.
  - **A denied offer's content is never kept on main.** Content uploaded for an offer main then denies is collected, where a member's denied edit used to leave its body on main until the next collection.
  - A reply whose parent main has not taken yet is refused with its parent, never denied, so a parent's commit that throws once no longer loses the reply beside it.
  - A spec, review or post of something main holds stays decidable from a node after the room or spec it depends on is deleted anywhere: a deletion main knows is a fact main decides by, not a reason for the node to revert the work.
  - A born-in spec whose room main deleted before the spec reached it is denied gone and re-homed, instead of being denied and removed.
  - Every settlement is announced and reported, as a denial is; every refusal is reported too, so a dependency that never arrives is seen rather than retried in silence.
  - Settlement never wedges a round: each offer settles in its own transaction, one that cannot be settled is reported, and a row re-created over main's deletion settles to that deletion rather than failing the round.
  - A refusal at ingest names both limits when main's is the tighter, and says to raise main's.
  - A withdrawal records no merge base, so work re-created over it starts over instead of being read as something main holds.
- **Every box holds exactly what main holds once it has synced.** After a round per box with no new writes, each node's copy of every synced entity equals main's: its fields, author, creator, revision, and deletion.
  - **A restore is never undone.** A node that adopted main's deletion of a spec, room, file or project used to keep treating it as its own pending delete. When main or another box restored or re-added the entity, that node pushed the delete again and main took it; with a restore to an older revision it parked a delete-versus-edit conflict instead, and a node that did not own the entity was told main denied a delete it never made. A deletion a node adopts is now main's, and a later restore or re-add is pulled everywhere, with no conflict and no denial.
  - **`sail conflicts resolve --theirs` takes main's version as main made it**, at main's revision and under main's author, a deletion's deleter included. It used to mint a revision of the node's own, credited to `main`, that main never held. `--mine` and `--merge` still write the choice over main's version as the node's own change. A conflict parked before this release does not name main's revision, so resolving it is refused, naming the fix, until `sail sync` re-records it.
  - **A room adopts every field main holds**, its creation time included, so a node that was offline while a room was deleted and re-created takes main's. A room deleted and re-created on one box before it syncs continues its revision counter and parks no conflict.
  - A message is recorded under the author it names on every box. A post made while acting as someone else, such as the review pipeline's verdicts, used to be credited to the poster's FDE on its own box and to its author everywhere else. The upgrade corrects the history of existing messages.
  - A revision main recorded with no author is adopted with none, not credited to `main`.
  - A project renamed on main reaches nodes as the rename's blocking deletion, under the FDE who renamed it, where nodes used to hold a plain deletion credited to `main`.
  - A change made on a node while its own earlier change is on the way to main is offered next, where it used to park a conflict with itself. If that earlier change had merged in main's edits, they are kept rather than reverted. A project renamed in that window keeps its rename's block. A change that clashes with a field main edited parks a conflict.
  - A node whose answer from main was lost keeps main's edits that its change had merged in, where the next sync used to revert them without a conflict. Each node now records what every change it sends was made from until main's answer arrives. A project deleted on a node and renamed there before a lost answer was recovered keeps its rename's block.
  - Starting an agent no longer records a revision of its run for the process ids only the box running it keeps, which left that box on a revision main never held until the run next changed.
  - A spec born in a room the node re-created over a deletion waits a round for its room, as one born in a new room does, instead of being denied and removed from the node.
  - A room a node deleted and re-created before syncing takes main's creation time as its base, so main's next edit of it is pulled rather than offered back under the node's name.
  - A change made on a node after an earlier change never reached main is kept, where main's answer about the earlier change used to be taken for the later one and the row reset to it.
  - A conflict the node parks while its own change is on the way to main closes once the FDE sets the clashing field to main's value by hand, instead of staying open until resolved.
  - A node upgrading from 0.46.2 walks main's heads once more: a `--theirs` resolve made under 0.46.2, a revision main recorded with no author, and a rename's deletion adopted without its block all converge on main's version in that round.
  - Two boxes that minted the same revision of an entity from the same content, such as the scrubbed form of a legacy project or the same edit made on both, no longer leave the node offering it on every round.
  - A local write landing during a round that leaves the row as the offer found it no longer parks a stale conflict; a write that changes it is offered next, and one that clashes with main's edit parks a conflict on that field.
  - A node's delete, restore and delete again while offline reaches main as the delete it is, instead of being undone by the next pull.
  - A re-create after a delete whose answer from main was lost reaches main, instead of being deleted again or parking a conflict with the node's own delete.
  - Main records a rename's tombstone under the author it names only when the pusher may write as that author, as for any revision.
  - A project made on a node under a name main has renamed away, after the node heard any earlier deletion of that name, reaches main instead of being deleted as a stale copy; a copy that never heard one still adopts the deletion.

- **A box's runs carry the handle main knows it by, and a live run is never rewritten.** Every run a box reserves — dispatch, build, restart, ad-hoc (`sail run`, `agent sweep`, the API), the review pipeline and its fix lane, and room wakes — carries the box's handle as both `node` and `owner`. Runs used to be stamped with a blank node, a stale handle, or the spec's or room's owner, and main then denied them, sometimes mid-run, and the node deleted them.
  - Main's `welcome` names the handle it authenticated the session as. A node whose configured sync handle is blank or another fails its round before offering or adopting anything, naming both handles and the fix.
  - One box syncs as each FDE. Main records the first box that syncs as an FDE and refuses any other, naming both boxes; an admin runs `sail fde release-box <handle>` on main after retiring the old box. Main's own FDE syncs from no box but main.
  - Every round, before anything else, a node stamps every run it made that main has never acknowledged with its handle. A run synced from another box is never stamped as this box's, even on a box that was main and holds every box's runs. A run main took whose answer was lost is acknowledged instead, keeping the stamp main holds it under. A run of this box's that an older release left acting for no one is stamped too, so main takes its completion.
  - **A lost answer never reverts or loses a change.** Main names, for each row a node asks after, the latest version it took from that box, and the node reconciles against exactly that. A change main made after taking the node's offer — an edit, or a delete — is never undone by the node pushing its offer again, and a field each side changed alone merges instead of parking. Every synced type, not only runs.
  - `sail host config set sync-handle` and `sail join` refuse to change the handle while a run main holds under the old one is live here or has changes main has not taken, naming each; on main, while any run the box executed is live. A node first asks main which runs it took whose answer was lost, and weighs those as held; when main cannot be asked, the change is refused. No sync round runs from that ask until the new stamps are written. Once changed, every run main has not taken is stamped with the new handle. A box becoming main stamps its unstamped runs. Removing an FDE releases the box it synced from.
  - Main takes a run only acting for the pusher. A run acting for no one is denied.
  - Main's version, pulled, denied or merged with the box's own change, never rewrites or removes a run or review still live on the box that executes it. It stays as it is and settles once finished. Another box's run is always adopted.
  - A room wake whose spec or room moved off the box before launch is refused and reserves nothing.
  - The reconciler finishes every dead session this box runs within one pass: superseded build sessions, room and full room runs of specs under way, a dead newest build run of a spec in review, and a newest build run whose recorded stop reached nothing that finishes runs, which it finishes without replaying the stop.
  - The reconciler reads a run as gone only when its container says so: a stopped or destroyed container runs nothing, while one incus cannot report, or a running one that will not answer a command, reads as alive. An `incus exec` that failed (incusd restarting) used to have live runs finished and their reservations and credentials released. A run whose recorded stop reached nothing that finishes runs is finished with that stop's exit code, and only a stop naming the run, or naming none, speaks for it — never another run of the same spec. A run read as not running is read again once its container has answered, so one command lost while incusd restarts never reads a working agent as gone. A spec's dead run is finished with the exit code its recorded stop carried, so a failed agent's work is never rescued into review as a clean finish.
  - The sync handle is stripped of surrounding space where `host.yaml` is read, so a box stamps its runs and recognizes them by one value.
  - A second box syncing as main's own FDE is told that FDE syncs from main alone; `sail fde release-box` cannot move it.
  - The lock files that serialize dispatch claims and sync rounds are created readable and writable by their group, so a root CLI and the API server can each take one whoever made it.
  - **The fleet floor moves to 0.46.3.** An older node pushes runs acting for no one, which main now denies, so main refuses it and tells it to run `sail upgrade`.
- **Main decides every pushed revision by the rule the doors ask.** Each synced type has one write rule in sail-core, and main's commit asks it for every revision a node pushes, after its compare-and-set and before it writes. The same edit gets the same answer through HTTP, the host CLI, the socket, the terminal and a sync. A member with an edited box database, or a crafted client, used to have almost every push committed.
  - A spec is edited, deleted or restored only by its owner or an admin, and its assignee changes only by an admin or a claim of an unassigned spec for oneself. A spec never moves to another room. Main used to commit anyone's edit, including taking someone else's spec, and the prune that followed then erased that FDE's spec, room, messages, runs and reviews on every box.
  - Restoring a deleted spec is its owner's or an admin's before any assignee change is decided as a claim, and a restore keeps the creator its tombstone recorded, whatever the push names.
  - A spec's id is reserved for its own room: a pushed spec is never born over a room, live or deleted, unless that moves no ownership (a node's own room reaching main first) or an admin pushes it. It would have handed that room, and the conversation in it, to the spec's owner. A room's restore keeps the creator its tombstone recorded, as a spec's does, and a node adopts the creator main holds, so both boxes agree on the room's owner.
  - A spec born in a room main has not received yet waits on the node for that room and lands the round after it, where it used to be denied and deleted there.
  - A room's later revisions, and a review and its verdict, are their owner's or an admin's. A review never moves to another spec, and a stage never moves to another review.
  - A run is its executing box's: its `node` is the pusher, it acts for the pusher or no one, a deleted run is never brought back, and every `principal` it carries names the run itself (`<family>/<marker><run id>`). A run naming another FDE or run could post as anyone.
  - A pushed revision names as its author (`_actor`) only the pusher, its box's machinery (`sail`) or a principal of a run the pusher owns, and a create names only the pusher as its creator. Admins are bound by this too. A principal of a run main does not hold yet is refused for that round and decided once the run lands, so an agent's spec lands the round after its run.
  - A post is authored by the pusher, a principal of any run it owns (in any conversation), or `sail` where a run it owns is in the conversation, and only where the pusher may post. An agent's post in another spec's room, where its FDE may post, is accepted at the socket and on main alike. A node holds an agent's post until main holds its run, in whatever conversation it runs.
  - A denied revision is settled as before: the node adopts main's version and keeps its own in history. Adopting main's review never deletes the finding rows the node holds, and the posts of a run main denied leave the node with it.
  - After an admin reassigns a spec away from a box, that box's status changes, reviews and pipeline posts on it are denied, and it adopts main's version. Its run is still its own to finish or stop, and a stop cancels the spec only when the stopper may change it. A review the box is still running keeps its row and findings until it finishes; a finished review main never held then leaves with the denial. A review run acts for the box's own FDE, not the spec's owner, so main takes it and what it writes.
  - A restart fails only the reviews this box executed, where it used to fail every running review, another box's included.
  - Local prune and main's decision on a node's prune ask one erase rule, with one set of texts: main's refusals now read like the CLI's (`Spec 'x' is assigned to 'bob', not you.`).
- **A node's writes speak for its FDE.** On a node, a credential naming an FDE other than the box's own acts with at most `viewer`: another FDE's token, passkey session, gateway key and terminal, admins included, read but write nothing there. Their writes would reach main as the box FDE's, on the box's session, and be denied. The box's FDE, its runs and its FDE-less credentials write as before.
- **A room's settings are its owner's.** A room's roster, wake, title and assignee are changed only by its owner or an admin. Setting a wake, or engaging or dismissing an agent, through a spec born in someone else's room is refused with the room owner's text, before anything is probed or launched; owning a spec born in a room still gives a voice there. Deleting a room refuses with room wording (`Room 'x' belongs to 'bob', not you.`, and `cannot change rooms` for a read-only credential), and so does managing a spec-less room's agents (still `not_your_spec`). Claiming an unassigned spec and setting its wake in one update is accepted.
  - Every door asks the rules it used to skip: drafting a follow-up acts on the source review under the review rule, and a read-only credential on the socket can no longer create a spec (`read_only_credential`, where a room session used to get a plain 403), refused before anything about the spec is checked.
- **New refusal code `forbidden_not_author` (403).** A write that names an author or creator its actor may not write as is refused with it.

## 0.46.2

- **Personal rooms are retired, and every one is erased on upgrade.** Rooms are created on purpose, from Mast: `GET /v1/rooms` no longer mints a room for its reader in every project, and rooms no longer render `personal_of`.
  - Sync every node, then upgrade main first. Its upgrade erases every personal room with its messages and runs, and each node adopts those erasures on its next sync. A standalone box erases its own.
  - Main decides on its own copy, as every erasure does: a run or spec a node started in a personal room and has not synced yet goes with main's erasure. A node's upgrade names each one.
  - Then upgrade every node. A node's upgrade removes the personal rooms main never held, which only that box ever had, and they never reach main.
  - **The fleet floor moves to 0.46.2.** An older node would mint a personal room and push it to a main that has already erased them all, so main refuses it and tells it to run `sail upgrade`.
  - A personal room deleted before the upgrade is erased too, with the messages and runs its deletion kept.
  - A personal room with a run still under way, or with a spec born in it, is left as an ordinary room, and the upgrade names it. The upgrade prints how many rooms it erased.
  - A personal room is recognized by its exact id, derived from its creator and project. A room whose id merely starts with `fde-` is untouched.
- **A spec left without an assignee is unassigned, and any member may claim it.** Creating a spec with no assignee used to assign it to whoever created it, which on the in-container socket was the run's principal (`claude/…`), leaving it undispatchable.
  - This holds through HTTP, the CLI and the socket (a run's credential or the box credential), and its identity room is unassigned too.
  - Its creator, the FDE who created it (a run records the FDE it acts for), may edit it while it is unassigned. Any member claims it with `sail spec update <id> --assignee <you>`; an agent claims it for the FDE it acts for. Dispatch refuses it until then, naming that claim.
  - Its room wakes on its creator's box, and a room-role run woken there may answer in it. Main accepts its creator's posts in its room through sync. Its creator may read the logs of, and stop, a run working it.
  - Once it is claimed, its room is the new owner's at every door: HTTP, the socket, the terminal and main's check of synced posts all decide who owns a conversation by one rule.
  - Owning a spec gives a voice in its conversation, so a spec born in a room is claimed, or created with an assignee, only by one who may already post in that room, and only for themselves; anyone else asks an admin to assign it. A claim never opens someone else's room.
  - A post about a spec born in a room whose row has not synced yet lands in that room.
  - A run's own FDE may still read the logs of, and stop, its run after the spec is reassigned.
  - A spec's creator now travels with it: main records a node-born spec's creator (the pushing FDE, when an older node names none) and keeps it, whatever a later push says, and every other box adopts it, the pushing node included. A spec main holds with no creator, such as one pushed before this release, gains one only from a push by that creator naming themselves.
  - An assignee is an FDE handle. The API refuses one shaped like a run's principal (`<family>/<id>`), and accepts a handle this box's roster does not know yet. The `--assignee` help of `sail spec create`/`update` and of the in-container `spec` CLI, and the spec skill, say so: the agent type goes in `--agent`.
- **The host CLI acts as the box's FDE.** The API token the host CLI uses names no FDE of its own: whenever it is used, it acts as the FDE the box's sync handle names at that moment, so a `sail spec create` or `update` on the box records that FDE and acts with its role. Changing the sync handle, or main's roster, takes effect on the next request; there is nothing to bind or migrate. A box with no sync handle has no FDE to be.
  - A machine token (any other token that names no FDE) acts as no FDE, with the role of the box's FDE capped by its minted role, so on a node it never acts beyond the FDE whose box it lives on. On a box with no sync handle it acts with its minted role. Such a token, the host token among them, used to act as admin on a node whatever the roster said.
  - On a node that has not pulled main's roster yet, or whose FDE main has disabled, a token acting for the box's FDE is answered `409`, naming `sudo sail sync`. A node that names no FDE of its own refuses such tokens and its CLI alike, naming `sudo sail host config set sync-handle`; its host token used to act as admin there.
- **A credential acts with its FDE's roster role.** One rule decides the role of every credential that names an FDE, whichever door it came in by: an API token, a passkey session, the box credential, the host CLI, a sync session, the SSH gateway and the terminal. Main's operator, or a standalone box's, is admin on it; every other FDE acts with the role main's roster gives it, capped by the credential's own role, so an API token minted as admin for an FDE since demoted acts with the demoted role.
  - A disabled FDE's credential is refused at every door; its API token and passkey session used to keep working on the HTTP API, and its session on the terminal and the sync server.
  - A node disables every FDE main's roster no longer lists, so an FDE removed on main is locked out on every box. A node used to keep it active.
  - Main never syncs against another box, even when asked with `sail sync --main` or `POST /v1/sync`: a round adopts the other side's versions and roster, which would overwrite the fleet's.
  - Dispatch, build and engage refuse to launch for a box whose FDE is disabled, rather than launching a run its credential cannot use.
  - A run's credential on the in-container socket acts with the role main's roster gives the FDE the run acts for, capped by its lane (member for an agent run, viewer for a room run), and is refused once that FDE is disabled. It used to act with its lane's role whatever the roster said.
  - Main decides whether a synced post is an admin's by the session's role, not by a second roster lookup.
- **A viewer node's CLI can no longer dispatch or stop.** `sail spec dispatch` and `sail agent stop` decide as the box's FDE with the role main's roster gives it, where they used to decide as a hard-coded admin. A stop needs write access. A preview (`--dry-run`) still describes what it would do.
- **Every box records the same author for a revision.** Main names the author it recorded when it accepts a node's push, and on a tombstone or an erasure it hands a node, including one a denial answers with. A node used to record `main` for these, and its own push without an author as `main` where main recorded the pusher. The new fields are optional on the wire.

- **A push main refuses on authority settles, and the node keeps syncing.** Main answers each such offer `denied`, with its current version. The node adopts that version, keeps its own in history, and carries on. It used to fail the round, and offer the same revision again every round.
  - Main denies a read-only session's offers, a message posted as someone the pusher may not post as, a reply to a message main does not hold, and a run whose provenance is not the pusher's. A denied offer never fails the offers beside it. A viewer's push used to fail whole, a forged author failed the push with every other offer in it, and a foreign run was answered as a race.
  - A message in a room main has never held is refused for that round and lands in the next, after its room. An agent's or the review pipeline's post waits on the node, with the replies under it, until main holds the run (and its spec) that decides it, so it is never denied for a run that simply had not arrived. A spec born in a room counts its runs as that room's, where main used to refuse their posts there.
  - A node-born entity main denies leaves the node: a denied message leaves its room with the replies this box posted under it. Every revision stays in the change log. A run from before the box's sync handle, with no node stamp, is such an entity.
  - A run still under way on the box is never rewritten or removed by a denial: its row, credential and room guard stay, and it settles once it has finished.
  - Adopting main's version counts as a pull, so it announces the board and resizes a project's container like any other pull.
  - A read-only session is asked for no content, so its push reaches main's decision instead of failing at the upload. Every offer is budgeted for main's answer, so a push's results fit the frame it fit.
  - Each denial is printed as main answers it, such as `spec auth: main denied this change — <reason>. Yours is in its history: sail spec history auth.`, by `sail sync` and a node's running server, even when the round later fails. `sail sync --json` and `GET /v1/sync` list them (`type`, `id`, `reason`). `sail sync --json` is now the same object as `POST /v1/sync`, which adds `message`.
  - On the wire a denial is a refusal marked `denied`, so a 0.46 node reads a refusal and fails that type's round naming the reason. For a read-only push and a forged author that is as before; a run main may not take from it, which a 0.46 main answered as stale, now fails its run type until the node upgrades. The sync floor does not change.
- **Every write names who is acting.** One `Actor` (handle, role, lane) is the identity of every write, bound by the entry point that makes it, and the change log reads it for every revision, tombstone and erasure. This changes no authority rule; it is where the next release enforces them.
  - Lanes: `CLI` (the box's operator), `API` (an HTTP token), `AGENT` and `ROOM` (a run's principal on the socket), `SYNC` (an FDE pushing to main), `MAIN` (a node adopting main's revisions) and `SYSTEM` (this box's machinery, recorded as `sail`).
  - The author in `sail spec history` and in `updated_by` is always the one who made that revision. A status-only or content-only change, a delete, a restore and a project move used to keep the previous editor's name; a synced row with no author used to read `sync`, and retention's erasures `sail-retention` (they now say `sail`, with origin `retention`).
  - A write with no actor bound is refused and leaves nothing behind.
  - A run, review or shared file keeps its author on every box. These have no author column, so a push used to record the pushing FDE on main and every box that pulled it recorded `main`.
  - On a node, the CLI writes as the box's FDE with the role main's roster gives it, and conflict resolution no longer runs as a hard-coded admin. A node whose roster has not synced yet refuses the write before touching anything and asks for `sail sync`; a preview (`run`, `agent sweep`, `agent stop --dry-run`) needs no identity. The CLI now prints a refusal's fix with its message.
  - Resolving a conflict keeps main's author on main's version. `--theirs`, or a merge identical to it, records the author main recorded; keeping mine or a different merge records the resolver.
  - A spec or room created through a machine token (one with no FDE) records no author and is left unassigned, so any member may claim it. It used to be assigned to the token's name.
  - Resolving the findings a follow-up spec addressed is journaled in one transaction, like every other review mutation.
- **A merge applies only to the conflict it was made from.** A merged record is a full record. A merge started before a round re-recorded the conflict with main's news used to revert that news: every field main had moved since read as a local edit back to its old value, and won main's compare-and-set.
  - `sail conflicts show <id> --template` prints the record to merge. Its `_conflict` key names the version of the conflict it was made from. `--merge` opens the same template in `$EDITOR`.
  - A merge without `_conflict` is refused (`400`). One made from an earlier version is refused (`409`) with nothing written. A round that brings no news keeps a template valid.
  - `--merge` refuses a conflict this box has written over before the editor opens.
  - A refused `--merge` keeps the edited file and prints its path, as reference for the redo.
  - `--merge-file` takes a template from `show --template`, so an agent or a script can merge without a terminal.
  - API clients get the same template from `GET /v1/conflicts/<id>?template=true`, on the web API and the in-container socket. A path suffix would collide with a file conflict's `project/path` id.
  - A merged record that is not valid YAML, or repeats a key, is refused as a bad request.
  - A clash on a field with several lines, such as a body, no longer breaks the template: main's value is commented line by line in its header, with any character YAML cannot carry, such as a terminal colour code, written as `\uXXXX`.
  - A template for a conflict that is not open is `404` on both APIs, as is a resolve of one; a stale merge is told to start again, not to resolve.
  - `--mine` and `--theirs` are unchanged: the side they choose and the merge base come from the same recorded conflict.
- **`$EDITOR` runs as git runs it.** `sail conflicts resolve --merge` and `sail project edit` run `$EDITOR` as a shell command with the file as its argument, so `EDITOR="code --wait"` works and an editor path with spaces is quoted, as for git. An unset or blank `EDITOR` means `vi` in both, and a failed editor names its exit status.

- **`sail upgrade --binary <file>` installs a local build**, such as an unreleased build or one for a box without internet access. It is the same install as a release download.
  - The file must be an executable for this platform.
  - It is staged beside the installed sail, and that staged copy answers `-V`, so the bytes checked are the bytes installed.
  - A build older than the installed sail is refused, as is combining `--binary` with `--check` or `--target`. Installing the bytes already installed changes nothing.
  - The installed sail knows `--binary` from this release on. To move a box on an older release to a local build, run the build's own upgrade: `sudo ./sail upgrade --binary ./sail`.
- **`sail upgrade` upgrades `/usr/local/bin/sail`, starting from that binary's version.**
  - It installs where install.sh puts sail, and compares the release with that binary's `-V`, not with the sail that is running.
  - An installed sail that cannot report its version is replaced, with a warning.
  - A `--target` older than the installed sail is refused, because migrations never run backwards.
  - With nothing installed there, `sail upgrade` and `--check` say to run install.sh.
  - Under a `SAIL_DATA_DIR` override it refuses, because an upgrade replaces this box's binary and restarts its services.
- **Host state names the installed binary.**
  - The `sail` user's forced commands and the `sail-api` and `sail-pty-host` units run `/usr/local/bin/sail`, whichever binary writes them.
  - `sail host service install` needs sail installed there.
  - Start, stop, status, logs and uninstall never need the binary, so a box whose binary is gone can still be cleaned up.
- **`sail migrate` limits what it changes to what the binary that runs it may change.**
  - Run by the installed sail, it converges the database and the host.
  - Under a `SAIL_DATA_DIR` override it is a rehearsal. It migrates and imports into that copy and touches no keys, units or services.
  - Any other binary is refused before it opens the database. The refusal names `sudo /usr/local/bin/sail upgrade --binary <it>` and the rehearsal.
  - The migrate that an upgrade starts never auto-upgrades, and neither does a rehearsal.
- **Legacy shared files sync without a mode conflict.**
  - Some files have no mode in their history; the content migration left them that way. Such a file keeps the mode its row records when the copy on disk lacks only bits the umask removed.
  - A copy someone made executable is imported as a new revision. So is a chmod back to a mode the history already records.
- `--dry-run` on `sail host service install` and `uninstall` no longer writes or removes unit files.

## 0.46.0

- **Archive keeps, delete restores, prune erases everywhere.**
  - `sail spec prune <id...>` erases specs with everything that belongs to them: the identity room (a shared room outlives the spec), the room's messages, the spec's runs and reviews, its events, every history entry, and the content only they referenced.
  - `--status archived,cancelled --older-than 90d [-p project]` is the admin's policy form.
  - A spec is pruned from archived, cancelled or deleted, and never while a run of it is unfinished.
  - A prune always reports first. The report comes from rehearsing the erasure in a transaction that is then rolled back, so it is what the real run does on this box's copy. Only `--apply` erases.
  - An erasure is terminal: a pruned spec id or project name is never used again. Creating one, or provisioning a project under a pruned name, is refused before anything is written.
  - The same method serves `POST /v1/specs:prune`, Mast's **Prune…** on an archived spec, and `sail project destroy --purge`, which now erases the whole project instead of tombstoning one row. It prints what it will erase before it confirms.
  - Authority: an owner (the assignee, or the creator when unassigned) or an admin. A policy or project prune is admin-only. Agents and read-only roles are refused.
- **Erasure is a kind of change-log entry.**
  - `change_log.kind` is `revision`, `tombstone` or `erasure`, backfilled from `deleted`. Every page entry carries it.
  - Main is the only author of erasures. A node's prune is an `erase` offer, and main decides it against its own copy; one round later every type on every box has converged. What main never saw is discarded on the node, never published. A policy prune runs on main only.
  - The journal refuses any write that would belong to an erased entity, on every box and every path.
  - A node applying an erasure removes only what main never acknowledged; what main held follows with its own erasure row.
  - Every box applies an erasure the moment a page, a need answer or a stale-push refresh brings it. It never reaches the conflict engine, so the erasure wins over an unsynced local edit and a stale push cannot resurrect the entity.
  - One erasure row per entity names who pruned and when. Erasure rows are never compacted, and a restore of a pruned spec is refused with that reason.
  - A room other specs were born into outlives the spec that minted it until the last of them goes.
  - The links between entities are declared once, in `Erasure`, not as foreign keys. Deleting a spec still keeps its runs, reviews and room so a restore brings them back, and sync never depends on the order entities arrive in.
  - The upgrade erases, on main only, what earlier releases orphaned (runs and reviews whose spec, and messages whose room, left no trace). It works one entity per transaction and resumes if interrupted.
- **History is bounded, content follows.**
  - Every box keeps each entity's newest 20 revisions, its synced base, and every tombstone and erasure. This is a compiled constant.
  - A node compacts what each round touched. Main compacts daily. `sail sync gc` compacts and then collects under the exclusive content lease, refusing inside a transaction.
  - `sail sync status` reports bytes freed.
  - A deleted spec can now be restored from any retained revision, including its tombstone, and brings back the identity room it minted.
  - `archived_at` and `cancelled_at` record when a spec entered those statuses.
- **Retention is opt-in.** A `retention` block in main's `host.yaml` (`prune_archived_after`, `messages`, `runs_after_finished`) makes main's daily sweeper prune by that policy, in bounded transactions, never taking an open agent question or a message a younger reply needs. Without the block nothing is erased that a person did not ask for, and nodes never evaluate retention.
- A deletion the old server writes while `sail upgrade` migrates is still recorded as a tombstone.
- **The fleet floor moves to 0.46.0.** A 0.45 box would read an erasure as a revision with an empty snapshot, so it is refused and told to run `sail upgrade`. Upgrade main first, then nodes.

## 0.45.0

- **Content syncs by hash, in chunks, never as base64.** Spec bodies and plans and shared files
  live once in a content-addressed blob store (SHA-256, content-defined chunks of 64 KiB–1 MiB,
  every chunk verified before it is written); rows and history carry hashes, so an edit to a
  title no longer re-journals the body and history grows by a hash per revision. The sync wire
  is a byte stream — a JSON line announces, raw bytes follow only a `chunk` — and content is
  deduplicated and resumable in both directions: a 1 KiB edit moves one chunk, an interrupted
  transfer resumes at the chunk it lost, and a node pulls a page's content one blob at a time so
  a page of many large files costs one manifest of memory. Shared files keep their permission
  bits end to end (a symlink's target, a local `chmod` the sync never recorded, an HTTP update of
  an existing file) and stream through ingest, sync, materialization and download; downloads
  send `Content-Length` and an `ETag` (the content hash) and answer `If-None-Match` with `304`.
  One cap replaces the 5 MiB limit: `limits.file_max` in `host.yaml`, 1 GiB by default, at most
  8 GiB, enforced from the declared length before a byte is read and by main on every upload.
  `sail sync status` reports bytes fetched and sent; `sail sync gc` frees content no live row,
  retained history or open conflict references. Upgrading migrates existing content one entity
  per transaction — resumable if interrupted, safe when two processes run it — and the fleet
  floor moves to 0.45.0: a 0.44 box cannot read a hash-only snapshot, and is told so.
- **Blobs hardening: one chunk loop, streams that outlive a stopwatch, a lease that means what it
  says.** The chunk and manifest runs over the sync wire have one definition, `ContentReceiver`,
  that both main's upload and the node's pull drive, with one vocabulary of failures (`protocol`,
  `unreachable`, `store`); main's replies to a bad upload are pinned byte for byte by a test, and a
  chunk the store cannot write is now reported as `store`, not `protocol`. Streaming a file out of
  a container is bounded by silence, not by the clock: `sail project files add` of a file that
  keeps delivering is never killed at two minutes, and one that stalls fails naming the command,
  the idle period and the bytes received. `host.yaml` is read once per command or request rather
  than once per file, so a corrupt file fails a bulk share or an upgrade's import before any file
  is opened, and every "too large" refusal is the same sentence, naming the cap in bytes and where
  to raise it (`limits.file_max` in `host.yaml`). A blob ingest inside a read transaction no
  longer silently skips the shared retention lease: only a write transaction, which holds the lock
  that makes skipping safe, goes without one. Retention is taken before the connection lock
  everywhere, so a read transaction runs its ingests under a lease taken before it opened, and an
  ingest or a collection that would take retention from inside a transaction is refused with a
  clear error rather than left to deadlock with a collector waiting on the connection.
- **The sync protocol-3 fallback is gone.** 0.44.0 let a node upgraded ahead of its main keep
  syncing over the whole-table protocol-3 wire for one release; that release is over. A node that
  meets a main still on 0.43 or older now fails the round saying main is on a sync protocol it
  cannot speak and to upgrade main — recognised by main answering `hello` with a message that
  names no `op`; noise on the channel is reported as noise, never as an old main. A `refuse` no
  longer carries the `error`/`error_kind` keys a protocol-3 node read, so a 0.43 node refused by
  this main sees the remedy inside an "Unrecognized sync response" line rather than on its own.
  The fleet floor stays `0.44.0`: this release is wire-compatible with every 0.44 box, so nothing
  already syncing is refused.
- **A conflict is decided on what the box holds now, and addressed by type and id.** `sail
  conflicts resolve` wrote the snapshot recorded at detection over whatever the box had written
  since; it now refuses (`409`) when the row has moved, ignoring latest-wins fields, until `sail
  sync` re-records the conflict. A spec and its room share an id, and the old lookup reported
  both as "No open conflict": `--type` on the CLI and `?type=` over the API say which, and an id
  parked under several types is refused naming them (`400`).

## 0.44.0

- **Sync ships the change log since a checkpoint, in bounded pages.** Sync protocol 4 replaces
  the whole-table-per-round wire: a round now costs O(what changed), a node can be seeded from
  any history size, and no entity table can grow past what one message may carry. A session opens
  with `hello`, is `welcome`d once (floors compare as versions; a node ahead of main is told the
  order, main first), reads main's high-water per type with `heads`, pulls only the types that
  moved as 16 MiB-bounded pages of the change log since a per-type checkpoint, asks `need` for
  main's rows of what it changed locally, and pushes in batches. Every adoption is one atomic
  store operation, no transaction spans the wire, and the checkpoint advances only after a page
  and only to what the node has seen, so a round that dies mid-page re-pulls it with nothing
  re-adopted. Main keeps `change_heads` (one row per
  entity naming its latest change) so every read the protocol makes is an index range, never a
  scan of history; `sync_state` becomes per peer and per type, carrying the old checkpoint into
  every type so no node re-seeds. Every box now has a stable sync id (`sync.box_id` in
  `host.yaml`; `sail join` and `sail host sync --as-main` mint one, `sail migrate` persists the
  hostname for a box that already has a role); it names the node in main's log, while who the
  node is stays the authenticated SSH principal. `sail sync` prints a line per type that moved or failed, `--json` carries a
  `types` list, and one type's failure no longer skips the others or the post-sync
  materialization. A run's process bookkeeping (`pid`, `watcher_pid`, `pid_ticks`, `log_path`,
  `transcript_path`) stays on the box that executes it. **Upgrade main first:** a 0.44 node still
  syncs with a 0.43 main through a one-release fallback and says so on every round; a 0.43 node
  meeting a 0.44 main is told to upgrade. The fallback is deleted in the next release.

## 0.40.0

- **The pty host ends a session loudly instead of wedging, and never leaks its ring.** A hardening
  pass over the per-container session host (no wire change):
  - **A pty or journal failure ends the session.** A read error, or a journal append that throws
    (a full disk), used to leave the gather thread joining a still-live child that nobody was
    draining — the session wedged live forever, unreapable, until an explicit kill. It now closes
    the pty, kills the child outright and reaps it first (a child that shrugs off SIGHUP and
    SIGTERM does not outlive its session), then every subscriber hears
    `SessionEnded(reason=io-error)`.
  - **Ring files are deleted and never leak.** A session's `~/.sail/sessions/<name>.ring` is removed
    when the session is killed, yielded to a dispatch, swept, or re-created — and when its create fails to spawn, so a
    bad working directory cannot litter rings that no quota counts — and every orphan ring is swept
    at host start (sessions do not survive a restart — there is no rehydration). New rings are
    created owner-only (0600).
  - **Input never pins a connection.** The write-token holder's keystrokes drain through a dedicated
    per-session writer thread over a queue bounded in frames and bytes (1 MiB queued plus in-flight,
    reserved before the payload is copied), so a child that has stopped reading (Ctrl-S, a stopped
    job) backs up to an `Err("input backlog")` instead of blocking the writer's connection or
    growing the host heap — and one stuck writer can no longer freeze the accept lane or every
    other connection.
  - **Unchecked failures answer `Err`, not a silent close.** An invalid session name, project, cwd,
    or terminal size is validated up front and refused with `Err`; any other runtime exception (a
    truncated frame, say) is a logged last resort that still answers `Err` on the open socket and
    then closes it cleanly, so Mast reads a real refusal rather than a transport fault it retries
    forever.
  - **Session names are validated as path segments.** A name like `../foo` is refused before it can
    escape the sessions directory or delete another session's ring.
  - **Backlog is bounded by bytes as well as frames.** A stalled subscriber's queue pauses at 1 MiB
    of live output (not only 4096 frames), and a resync replays a bounded 256 KiB tail rather than
    the whole 4 MB ring on the link that just proved too slow. Writer and geometry notifications
    coalesce to the latest of each, so a client that stops reading and hammers `TakeWrite` or
    `Resize` cannot grow anyone's queue past the caps.
  - **`sail session attach` narrates a refused keystroke.** The host's `Err` for a rejected input
    (no write token, or a full input backlog) is rendered inline as `[sail: …]` instead of being
    dropped, so a paste that outran the session is visibly incomplete rather than silently short.
  - **Resource caps.** Sessions per FDE (32) and subscribers per session (16) are each refused with
    an `Err` naming the cap, and each admission is atomic with its registration, so concurrent
    creates or attaches cannot all take the last slot. Recreating another owner's corpse (an admin
    reusing a name) counts as a new session against the recreator's cap; only replacing your own
    corpse takes no extra slot. A socket over the host's connection cap
    (256) is closed before a byte of it is read: a peer that opens many and never speaks holds no
    handler, descriptor, or frame past the cap.
  - **The host logs one line per attach, refusal, and exception** (principal, session, reason) to its
    journald unit; wire `Err` strings no longer name another FDE's ownership.

## 0.39.2

- **An attach replays everything the journal holds.** The pty host used to replay at most 256 KB of a
  session's 4 MB journal on attach and on a flow-control resync, because the tail crossed as one
  frame and the wire refuses frames over 1 MiB. The tail now crosses as a run of `Output` frames of at
  most 256 KiB inside the same `ReplayBegin`/`ReplayEnd` bracket, so a client that reconnects (a Mast
  relaunch) sees the whole history the host has. No wire change.

- **Pty sessions tell programs what terminal they are in.** The child of every host-owned session
  now inherits `COLORTERM=truecolor`, `TERM_PROGRAM=mast` and `TERM_PROGRAM_VERSION=<sail
  version>` beside `TERM=xterm-256color` (which stays: containers ship no other terminfo), so
  agent TUIs detect truecolor and identify the host without probing.

## 0.39.1

- **Fix: `sail session ls --json` and `sail dispatch --json` died in the native binary** with a
  GraalVM unsupported-feature error (record components unavailable for reflection) — the records
  `CliJson` prints were never registered for reflection, and only the JVM tests exercised them.
  They are registered now, and `_pty-selftest` (the release smoke test) stringifies one of each
  on every platform so a future `--json` record cannot ship unregistered.

- **Breaking (pty wire): SAILPTY3.** The session host answers an admitted `Hello` with `Welcome`
  carrying its boot id — a fresh id per run of the host process, the same on every connection
  until the host restarts — so a terminal client that remembers the id a session was last seen
  under can tell "the host restarted and lost it" from "it ended". The handshake magic moves to
  `SAILPTY3`; a client speaking `SAILPTY2` is refused by name (Mast renders its skew card until
  one side is upgraded). `sail session ls --json` now includes `host_boot_id`. The pty host
  restarts on `sail upgrade`, as before.
- **Pty sessions carry an incarnation id.** Every create mints an `instance_id` for that life of
  the (reusable) session name; it rides `SessionInfo` on the wire (SAILPTY3), `sail session ls
  --json`, and the data of every `pty_session_started/attached/ended` event. A client that only
  ever saw two corpses of one name can now tell which life each belonged to — the fact Mast's
  ended cards settle their reason on, instead of the name's newest event.

- **Breaking (CLI + API):** the one-shot invite lane is gone — one verb per primitive. `sail spec
  invite` no longer exists and `POST /v1/rooms/{id}/invite` answers 404 with a pointer to the two
  verbs that remain: add a member (`sail spec engage`, `POST /v1/rooms/{id}/members`) to converse,
  dispatch a spec to delegate. `Lane` has no `invite`/`invite-full` values; a historical invite run
  row lists as plain history with an unknown lane but keeps the contract it was minted under — a
  plain invite still running across the upgrade stays viewer-tier, neither role's stop enters the
  review pipeline, and stop and the reaper still address the row — and old `invite-<run>`
  snapshots keep their provenance label. CLI copy now says member: `spec engage` adds a member, `spec disengage`
  removes one.

- Personal rooms: every FDE gets one room per project, minted lazily on their first rooms read
  (`GET /v1/rooms`, filtered or not) — id `fde-<handle>-<project>-<fingerprint>`, where the
  fingerprint of the exact handle/project pair keeps the id unique when the readable slug is not
  (case and punctuation fold, a hyphenated handle shifts the boundary, a long pair truncates) —
  titled by the handle, assigned to the FDE, the project's default agent seated as its first
  member. Rooms render `personal_of` (the handle) on a personal room so clients pin it without
  re-deriving the id. Every field derives from the
  FDE and project rows, so two boxes minting the same room converge as a no-op on sync; a deleted
  personal room stays deleted until the FDE recreates it.

- Wake defaults derive from the roster instead of a stored value: a room whose `wake` is unset
  runs `on` with one member or none and `mention` with two or more, so a multi-member room answers
  only when addressed. An explicit `wake` a human set is never overridden — including `off` on a
  room with a seated member, which previously answered regardless. Rooms now render
  `effective_wake` beside the stored `wake`. No data migration: existing explicit values keep
  their meaning; existing nulls take the derived default.

- The pty event lane is measured, and its live half now exists. A `pty_session_*` row the pty
  host cannot write no longer vanishes silently: each drop leaves one structured line in the
  host's journal (`sail-pty-host.service`) and bumps a drop meter file beside the pty socket that
  the new `sail session ls --json` surfaces (`event_drops`: count, last type, cause, timestamp).
  The fail-open contract is pinned on both sides of the seam — `PtySession` now swallows whatever
  a `PtyEvents` implementation throws, so a session can never die or stall because eventing
  failed. And the lane's structural gap is closed: the pty host writes its event rows straight
  into the events table from its own process, so `/v1/events/stream` — the live lane mast treats
  as its accelerator — never carried them at all; the server now bridges new pty rows onto its
  event bus every 2 seconds, and the audit persister skips pty facts (persisted at source) so a
  row is never written twice.

- `sail agent attach` resumes a completed run's conversation inside a host-owned session
  (`resume-<run id>`, pinned to the run's room) instead of a raw `incus exec` tty: `Ctrl-]`
  detaches and the conversation lives on, attaching again joins the live session instead of
  forking a second agent, the run's room lists it like any room session, and a `spec create` from
  the resumed conversation is born in the run's room. Host-owned conversations respect the
  reservation gate: when a dispatch reserves the repos a resumed conversation works in — by exactly
  the dispatch gate's rules, so a read-only room wake displaces nothing — the reservation ends the
  session, attached or detached, with the reason in its stream and on its `pty_session_ended` room
  event, and the dispatch proceeds. New host-inbound pty wire verb `Yield(session, reason)`.

- `agent_session_started` now carries `run_role`, so clients can light presence the moment a run
  launches instead of waiting for its first tool call — the seconds between "message sent" and
  "agent working" shrink to the wake debounce plus launch.

- An agent can be engaged in a spec's room: it joins the conversation and answers every human
  message until dismissed. `sail spec engage <id> --agent <a>` (API `POST /v1/specs/{id}/engage`)
  records the engagement on the spec row as one atomic synced value — agent, mode, model,
  engaged-at as a single JSON column, so field-level sync merging can never stitch two boxes'
  engagements together — and `sail spec disengage` clears it; both transitions publish room-visible
  events (`spec_engaged`, `spec_disengaged`). **Full access is the default mode**: conversations
  produce artifacts (diagrams, drafts, files), so an engaged agent works in the workspace, drafts
  spec bodies, and creates sibling draft specs, guarded by the same one-writer-per-repo
  reservation a build takes per turn. An engage-time rollback snapshot is opt-in
  (`--snapshot` / the dialog checkbox) and off by default — on the `dir` backend a snapshot is a
  slow full filesystem copy, and the choice to skip it belongs to the human.
  `--read-only` is the explicit narrow choice, enforced by the harness and offered only where
  enforcement exists (claude-code today); full mode works on every agent, so codex is a
  first-class conversationalist. An engagement did not take effect until its snapshot succeeded —
  a failed payment publishes `spec_engage_failed` and engages nobody.
- Engaged rooms converse at conversation speed. The wake reactor answers every human message in an
  engaged room regardless of wake mode or dispatch history — a fresh chat room needs no build-run
  ancestry — with a 5-second debounce and **no post-finish cooldown** (the 30s/10min rules remain
  exactly as shipped for non-engaged specs). Turns resume the engagement's own conversation: the
  session selector is now role- and agent-filtered, so a build's session can never reopen under a
  chat turn's tool cut. A read-only chat turn runs alongside its own spec's live build (the gate's
  same-spec rule now applies within working lanes and within chat lanes, never across); a full
  turn defers on the build through its repo claim and fires on the build's stop, which — like a
  message landing in a turn's tail — re-evaluates the room for owed turns (newest human message vs
  newest chat-turn start; derived, never bookkept). A periodic engagement sweep backstops the
  event edges. Chat turns skip the read-only worktree fingerprint in full mode and never snapshot.
- Engaged turn prompts drop "when you have contributed, stop": a turn ends, the engagement
  continues, and the agent is told it will be resumed for the next message — never to say goodbye.
  The wake prompt also stops promising read-only git the allowlist deliberately denies.
- The one-shot read-only invite is retired, superseded by engagement (the API refuses it naming
  the replacement); `sail spec invite` is now the task-shaped lane it always really was — one
  full-access turn, snapshot first. Slack stops narrating conversation plumbing: a chat or invite
  turn's clean exit ("Agent stopped (exit 0)") no longer posts, while failures and build stops
  keep their narration.

- A room message now wakes the agent when no run is live. A new `room-wake` reactor on
  `spec_message_posted` (local and sync-arrived alike) runs on the dispatch-owning box — the one
  whose handle is the spec's assignee, so the fleet has exactly one waker per spec — and launches
  a real run through the same reservation machinery as dispatch: run role `room`, principal
  `<agent>/room-<runId>`, run credential, watcher, and guardrail ceiling. The gate learns the
  chat lane explicitly: a `room` run reserves no repos and conflicts only with runs of its own
  spec, so a wake and a dispatch on one spec serialize while a chat never blocks another spec's
  build. Timing is time-based only — a 30s debounce batches messages into one wake, a 10-minute
  post-finish cooldown kills the thank-you refire and covers the review loop's inter-iteration
  gaps, and any live run suppresses the wake outright (the relay owns delivery then). Wake
  policy is the per-spec synced `wake` field (`on` | `mention` | `off`, default `on` once
  dispatched; `spec update --wake`, shown by `spec show`); only human authors ever wake — agent
  and `sail` posts are structurally excluded, so no storm loops. The wake resumes the spec's
  most recent recorded conversation when one exists (`claude --print --resume` /
  `codex exec resume`, session ids validated before touching an argv) and otherwise primes a
  fresh session with the spec body and room tail; either way the prompt's rendered messages seed
  the delivery ledger. The chat is read-only by contract and structurally excluded from review:
  stop signals now carry `run_role` (env, session file, watcher, reconciler), the pipeline and
  the lifecycle reactor ignore `room` stops even on a spec parked in `review`, the stop gate
  skips the git protocol for the chat while keeping the room last-look, and a wake turn that
  somehow moved a repo's HEAD surfaces as a loud `guardrail_triggered` event with the changed
  files — never a review.

- The room lane's read-only contract is enforced by the harness, not promised by the prompt. A
  `room` run launches Claude Code without `--dangerously-skip-permissions`: the tool set is cut
  to `Bash,Read,Grep,Glob` (no Write, no Edit) and the only auto-approved commands are the
  `spec` CLI — the lane's one write, posting the answer — plus `cd` and read-only git; print
  mode denies everything else, so a prompt-injected instruction to edit the worktree fails at
  the harness. Codex wakes decline loudly instead of launching unenforced: its only sandbox
  (bubblewrap) needs user namespaces, which incus containers block, so no codex mode both runs
  commands and honors a read-only boundary. On the socket, a room credential now resolves to a
  read-and-converse principal (`viewer` role, `room` lane): every spec mutation — status,
  metadata, content, restore, delete, create, other specs' rooms — returns 403 at the API
  boundary, and the one allowed write is posting to its own spec's room. The commit guard's
  baseline moved host-side into the run store (out of the guarded agent's reach, consumed on
  first read) and now records a worktree digest alongside each HEAD, so an uncommitted edit is
  as loud as a commit. Wake session resume is node-local: a session id recorded by another box
  never becomes a `--resume` argv, and the fresh-prompt fallback keeps the spec body.

- Every run now knows its agent session. A new `sail-session-report` SessionStart hook (both
  CLIs; Codex's payload verified to carry the same `session_id`/`transcript_path` fields) posts
  the conversation's identity to the run row over the run-credential lane
  (`POST /v1/run/session`), last write wins — a resume, clear, or compact restart re-reports the
  new conversation, and the fix lane reports without `SAIL_SPEC_ID`. The three fields
  (`session_id`, `session_source`, `transcript_path`) replicate with the run (old-shape
  snapshots derive nulls) and surface on runs listings and `latest_run`. `sail agent attach` now
  has honest semantics per run state: a completed run resumes its recorded conversation exactly
  (`claude --resume <id>` / `codex resume <id>`, never an interactive picker; loud fresh
  fallback when no session was recorded, `--dry-run`/`--json` show the exact argv), and a live
  run is refused with the real lanes named — reply in its spec room to steer it, or stop it
  first; live observe/attach arrives with the PTY session host.

- A `still_open` ruling's evidence now travels with the finding instead of being discarded. The
  carried row stores the ruling's evidence (`carry_evidence`, newest ruling wins; the
  `carried_from` chain keeps the older ones), the next fix task renders it as a reproduction
  claim the agent must answer — with code or a dispute argument, never a bare "already fixed" —
  and the re-review prompt shows each carried finding alongside its own prior scenario. The
  review prompt now asks `still_open` verdicts to describe the exact residual scenario.
- Fix-lane room posts are attributed honestly. Rejoining a review run stamps the invocation's
  own identity on the run row (`<agent>/fix-<reviewId>` for the fix lane,
  `<reviewer>/review-<reviewId>` for a reviewer), journaled so it replicates — the room's audit
  trail names the lane that wrote each post instead of crediting the fix agent's work to the
  reviewer's principal.

- Room messages now reach the live run. A new `sail-room-relay` PostToolUse hook delivers replies
  posted mid-run into the agent's context after its next tool call, on both Claude Code and Codex
  (both honor `additionalContext` injection). Each run keeps a `run_delivered_messages` ledger —
  exact message identities, node-local, never synced — seeded with what the dispatch or fix
  prompt already rendered, so a message that syncs in from another box late is still delivered
  whatever its id; delivery is run-credential-scoped through the local API's new
  `/v1/run/messages` inbox (with `has_more` when a batch is capped) and exact-id acknowledgement,
  so the fix lane gets delivery without `SAIL_SPEC_ID`. The stop gate takes a last look:
  undelivered messages block the stop once (their bodies are the reason, acknowledged before the
  block — a failed acknowledgement fails open and retries) under a marker separate from the
  git-protocol nudge, so each concern blocks at most once. The fix task now renders the room
  conversation, the dispatch prompt teaches `spec comments` as the read verb, and the spec-room
  composer states the delivery contract while an agent is working.

- Review findings now have identity, verdicts, and a dispute lane. The re-review receives the
  previous review's open findings and must rule on every one (`fixed`/`still_open`/`disputed`,
  evidence required to resolve) inside a verdict envelope — the only reviewer output shape the
  parser accepts; a bare findings array errors the stage. Unruled findings carry forward as the
  same finding (a `carried_from` chain), keep failing the gate, and escalate by name once they
  survive `max_finding_age` fix iterations (default 2). The fix agent disputes a wrong finding by
  arguing it in the spec room instead of coding around it; the reviewer rules, disputed findings
  skip the gate but surface in the room verdict for the human. "N open findings" after a pass now
  means exactly N unresolved sub-gate findings.

## 0.17.3

  process held a write lock could fail outright with "database is locked" — the CLI, the
  in-container `spec` helper, the sync server, and the reconciler all open through that path.

  grouped by /64), and authenticated callers stay throttled by credential. SSE is charged once at
